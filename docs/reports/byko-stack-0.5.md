# byko-stack 0.5 — 요청 중심 루프로 재설계

2026-11-01. Claude Code용 byko-stack을 spec 주도 단계별 스킬 묶음(0.4.0)에서 요청 하나를 끝까지 끌고 가는 루프로 다시 짰다. 이 문서는 무엇을 왜 바꿨고 무엇을 어디까지 확인했는지를 적는다. 확인한 것과 확인하지 못한 것을 구분한다.

## 먼저 볼 것: 행동 평가에서 남은 실패

이 판은 구조를 바꿨지만, 단일 실행 행동 평가에서 아래 실패가 남았다. 정한 보정 횟수(1회)를 다 썼으므로 고치지 못한 채로 적는다. 향상은 주장하지 않는다.

| 실패 | 관찰 | 해 본 수정 | 남은 원인 가설 |
|---|---|---|---|
| 가벼운 일이 무겁다 | 몇 줄 수정에 285초·출력 27.3K 토큰. 플러그인 없음은 52초·4.9K(약 5.5배, 사전 등록 통과선 2.5배) | 검토자의 확인 깊이 상한(메인 실행 기록 대조 우선, 설치·퍼즈 금지, 가벼움은 관점 1~2), 리포 안내는 변경에 닿는 것만 → 509초·71.6K에서 줄었다 | 진입 스킬 본문 자체(약 5K 토큰)와 기록 만들기·독립 검토 1회의 고정 비용. 메인 effort xhigh에서 절차가 그대로 실행된다 |
| 민감 경로의 두 번째 싱크를 놓친다 | "간단한 거야" 요청에서 같은 주입 싱크가 legacy_attrs에도 있음을 0.4.0처럼 놓쳤다(6/7) | 없음(이번 보정 범위 밖) | 연결 조사가 요청이 가리킨 위치에서 멈춘다. 민감 축이 검증 엄밀성으로 이어지지 않았다 |
| 연결된 B 사례가 너무 오래 걸린다 | 첫 평가는 후보 작성자 3명을 백그라운드로 띄운 뒤 진행 보고로 턴을 끝냈다(`-p`라 세션 종료). 재평가는 끝까지 진행해 수정이 숨긴 검사 26/28(플러그인 없음 24, 0.4.0 22)로 가장 높았지만, 설계 검토 1회·구현 검토 2회(검토자가 성능 스크립트까지 돌림)로 60분 상한에 걸렸다. 플러그인 없음은 392초 | 결과가 다음 단계의 입력인 위임은 포그라운드(`run_in_background: false`)로, 진행 보고로 턴을 끝내지 않기 | 후보 비교·설계 검토·재검토가 이 크기의 수정에도 모두 켜진다. 검토자의 확인 깊이 상한이 중간 크기 변경에서는 약하다 |

같은 평가에서 확인된 개선도 단일 실행 사실로만 적는다. 이름 없는 일반 요청에서 진입 스킬이 매번 불렸다(0.4.0은 7회 중 0회). 거절된 PR 검토에서 신판은 회귀를 재현해 머지를 막았다(0.4.0은 머지 가능으로 판정). 진단만 요청한 사례에서 코드를 바꾸지 않았다.

## 왜 바꿨나

| 관점 | 내용 |
|---|---|
| 누가 | 여러 리포에서 이슈·요청을 맡기는 사용자와, 그 일을 하는 Claude Code 메인 세션·서브에이전트 |
| 언제 | 기능 개발·고도화, 제보·알람의 진단과 수정, 중단된 작업의 재개, 정해진 경로에 맞지 않는 작업 |
| 어디서 | 리포마다 컨벤션·정책·데이터 구조·테스트·배포 방법이 다른 환경 |
| 무엇을 | 요청을 목표 복원 → 연결된 근거 조사 → 설계 → 구현 → 검증으로 진행하고, 문제가 드러나면 원인 단계로 되돌아가는 하나의 루프 |
| 어떻게 | 사람에게는 조사로 풀 수 없는 정책·의도 결정만 가져온다. 작은 일은 가볍게, 복잡·민감한 일은 근거로 고른 오케스트레이션과 독립 검토로 한다 |
| 왜 | 하네스가 Claude의 실제 동작을 모른 채 만들어져 지침에 쓴 것이 그대로 동작하지 않았다. 일부만 보고 판단하고, 사람이 반복해서 개입하고, 가벼운 일이 때로 무거워지고, PR이 사람 리뷰에서 걸렸다 |

0.4.0의 실제 동작도 확인했다. 아래 평가의 선행 실행에서 0.4.0은 스킬 이름 없는 일반 요청 7회 중 한 번도 스킬을 부르지 않았다. 의도한 흐름이 실행되지 않은 것이다.

## 무엇이 바뀌었나

| 구분 | 0.4.0 | 0.5.0 |
|---|---|---|
| 스킬 | spec-designer, spec-dev, eval-gate, review, codex-eval, agent-harness-builder | `work`(진입과 루프), `design`(방법·검증 기준·후보 비교), `review`(독립 검토 구성·종합·인계), `review-run`(독립 검토 실행) |
| 에이전트 | code-explorer, implementer, evaluator, reviewer | code-explorer, implementer, reviewer(evaluator 흡수), proposer(후보 작성, 새로) |
| 공유 문서 | shared/workflow.md 등 4개(Read로만 읽힘) | 없음. 필수 규칙은 실행 지점인 스킬·에이전트 본문 앞부분에 둔다 |
| 작업 기록 | 단계마다 spec·plan·HTML 문서 | 대상 리포의 `.byko/work/<날짜-이름>/`에 `brief.md`(일의 정의)와 `record.md`(진행). 독자가 다를 때만 `design.md` 같은 파일을 나눈다. git이 무시하는 폴더라 PR에 섞이지 않는다 |
| 진행 | 스킬끼리 다음 단계를 제안하고 사람 승인을 기다림 | `record.md`의 열린 항목이 다음 행동을 정한다. 실패 유형별로 원인 단계의 항목을 다시 연다. 승인 대기 단계는 없다 |
| 지시 총량 | md 26개, 131,011바이트 | md 16개, 62,624바이트(Codex 전용으로 옮긴 agent-harness-builder 포함). Claude 쪽 스킬·에이전트는 44,290바이트 |

- **진입.** `work`는 Claude가 일반 요청에서 부르고, 사용자가 `/byko-stack:work`로도 부른다. description에 강도어를 쓰지 않고 요청 유형과 경계를 적었다. `design`과 `review`는 따로 불러도 된다.
- **독립 검토.** 설계 검증과 구현 검증에 무게를 둔다. 첫 검토자는 작성자의 판단이 없는 `brief.md`(설계 검증이면 `design.md`도)만 읽는다. 검토자는 이름 있는 플러그인 에이전트(`byko-stack:reviewer`)로 띄우고 포크는 쓰지 않는다. 출하하는 변경에는 독립 확인이 최소 1회 있다. 가벼운 일은 검토자 1명, 관점 1~2개다.
- **압축 대비.** 진입 스킬의 필수 규칙(1~7절)은 실측 4,472토큰으로, 압축 뒤 다시 붙는 앞 5,000토큰 안에 있다.
- **쓰지 않는 것.** 훅, Task 도구, 플러그인 settings의 `agent`, 에이전트 팀. 필요가 확인되지 않았다.

## 어떻게 정했나

1. 사용자 발화 원문, 이전 Codex 대화, pstack·Codex판·Claude 공식 문서·실사용 근거에서 검토 기준을 먼저 만들었다.
2. 설계 방법을 독립 판정으로 정했다. 서로 다른 출발점 셋(경로·기록·확인)에서 전체 설계안 3개를 독립으로 받았다.
3. 출발점 표지를 가린 판정자 2명이 고정 루브릭으로 채점했다.
4. '기록' 출발점 안을 골랐다. 두 판정이 모두 다른 안의 검토 구조(검토자가 작성자의 자기 판정을 읽음)를 구조 결함으로 봤다. 고른 안은 첫 검토자가 작성자 판단 없는 일의 정의만 읽는다.
5. 다른 안의 좋은 점 6개를 접목했다. 예: 후보 작성 전용 에이전트, 선택·생략 사유를 검토자가 읽는 곳에 두기.

### 행동 평가

- **대상.** 공개 프로젝트 Python-Markdown, 고정 commit `3ade80d`. 실제로 닫힌 이슈 #1643과, 같은 이슈에 AI가 만들었다가 메인테이너 리뷰에서 거절된 PR #1645를 사례로 썼다.
- **비교 축.** 0.5.0(신판), 0.4.0, 플러그인 없음.
- **실행 조건.** Claude Code 2.1.316, `claude-opus-5-5[1m]`, effort xhigh. 구독 인증으로 돌렸다(init의 `apiKeySource` none을 실행마다 확인). 사용자 환경 설정을 격리하고 네트워크를 차단했다.
- **실행 방식.** 신판은 사례마다 1회 돌렸다. 0.4.0과 플러그인 없음은 설계 전에 같은 하네스로 돌린 선행 실행을 기준선으로 썼다.
- **해석 한계.** 반복이 없으므로 모든 비교는 단일 실행이다. 향상을 일반화하지 않는다.

시간은 벽시계 초, 토큰은 출력 토큰(서브에이전트 포함)이다. 기준선(0.4.0·플러그인 없음)은 선행 실행 결과다. 신판 첫 평가 뒤 드러난 과잉 검증을 한 번 보정하고 실패한 사례를 다시 돌렸다(재평가).

## 사용자 대신 정한 결정

- **평가를 `claude -p`로 돌렸다.** 사용자는 API 키 과금을 거부했다. 실측해 보니 이 환경의 `-p`는 구독 인증으로 돈다. 세션 안 주입 방식으로는 진입·발견·압축을 볼 수 없어서 평가에 한해 `-p`를 썼다.
- **agent-harness-builder를 Codex 전용 경로(`codex/skills/`)로 옮겼다.** `.codex-plugin`의 skills 경로도 그쪽으로 바꿨다. Codex 마켓플레이스가 이 디렉터리를 노출하기 때문에, 새 Claude 스킬이 Codex 쪽 목록에 나타나지 않게 하려는 것이다. Claude 쪽에서는 이 스킬의 호출 기록이 없었다.
- **spec 흐름 스킬, codex-eval(사용자 결정), byko-doc.py와 HTML 자산, 공유 문서를 제거했다.** 0.4.0의 유용한 규칙(질문 정책, 범위 규율, [TBD] 보류, BOUNCE_BACK 등)은 새 스킬·에이전트 본문으로 옮겼다.
- **사용자 지시로 작업 규모를 줄였다.** 별도의 설계 검증 라운드를 두지 않고, 두 판정자의 깊이 확인으로 대신했다. 행동 평가에서 반복, 숨긴 변형, 실제 환경 짝 실행을 하지 않았다.

## 확인하지 못한 것

- 대화형 세션에서 `review-run`(포크 스킬, `background: false`)이 같은 턴에 기다리는지. `-p`에서만 확인했다. 대체 경로(Agent 도구 위임 + 기록의 막는 항목)가 본문에 있다.
- 실제 자동 압축 뒤 진입 스킬 앞 5,000토큰이 다시 붙고 `record.md`가 다시 읽히는지. 본문 토큰만 실측했다.
- Codex가 `.codex-plugin`의 `./codex/skills/` 경로를 읽는지. Codex로 실행하지 않았다.
- 반복 실행의 분산, 숨긴 변형, 실제 사용자 환경(전역 CLAUDE.md·개인 스킬)에서의 짝 비교.
- 평가하지 않은 사례: 작업 중 사용자 발화 처리, 압축·세션 교체 뒤 재개, 사람 접점, 리포 규약 충돌 등.
- `plugin eval`처럼 셸 도구가 없는 세션에서는 진입 스킬의 기록 목록 주입이 호출 자체를 멈출 수 있다(공식 문서 기준).
- 설치·업데이트 경로. 평가는 세션 한정 로드(`--plugin-dir`)로 했다.
