# byko-stack-codex: 실제 실행으로 본 AS-IS와 TO-BE

## 먼저 확인된 결론

같은 작은 기능을 두 버전으로 설계·구현·검증했다. **최종 제품 코드는 바이트까지 동일했고 공통 행동 검사도 둘 다 14/14 통과했다.** 이번 사례에서 확인된 변화는 더 정확한 코드를 생성했다는 것이 아니라, **작업 문서 9개를 2개로 줄이면서 독립 문서 검토를 추가하고 구현 검토까지 자동으로 연결한 것**이다.

AS-IS도 이번 요청에서는 사용자에게 다시 묻거나 후속 명령을 요구하지 않고 완료했다. 기존 버전은 반드시 중단하고 새 버전만 자율 실행한다는 설명은 이 데이터와 맞지 않는다. 또한 독립 검토는 1회에서 2회로 늘었으므로 모든 수행 단계·비용이 줄었다고 말할 수 없다.

## 1. 비교 조건과 데이터 출처

| TO-BE | 이번 개선 후 working tree의 0.3.0을 별도 읽기 전용 사본으로 고정 |

초기 코드·요청의 파일별 SHA256이 두 작업에서 동일함을 확인했다. 스킬 사본의 tree hash는 [experiment.json](evidence/experiment.json)에 있다. 원래 프로젝트는 [initial-fullcycle](evidence/initial-fullcycle/REQUEST.md), 실행 기록은 [AS-IS](evidence/run-fullcycle-a.md)와 [TO-BE](evidence/run-fullcycle-b.md), 최종 변경 전체는 [AS-IS patch](evidence/fullcycle-a.patch)와 [TO-BE patch](evidence/fullcycle-b.patch)에 보존했다.

파일 수·줄 수·문자 수와 코드 hash는 실제 파일에서 계산했다. 역할 호출과 테스트 명령 순서는 실행 agent의 계측 기록 및 reviewer 결과를 근거로 한다. 임의로 요약한 행동 번호를 전체 도구 호출 수로 집계하지 않았다. 실행 중 reviewer 슬롯 경합이 한 번 있어 대기한 후 평가했으며, 소요 시간·속도 비교에는 사용하지 않았다. 토큰 사용량·비용도 측정하지 않았다.

## 2. 실제로 요청한 기능과 최종 결과

사용자 요청의 핵심은 다음이었다.

> 작업을 다시 등록했을 때 중복 항목이 생겨 원래 작업을 추적하기 어렵습니다. 이 기능을 설계하고 구현·검증까지 완료해 주세요.

목적에 포함한 요구사항은 정확히 같은 label의 재등록 시 첫 기존 id 반환, 파일 내용·수정 시각 보존, 재개방 후 동일 동작, 문자열 차이 구분, 기존 JSON·API·데이터 보존, 새 label의 `max(id)+1`, 기존 중복 데이터의 무변경이다. 단일 프로세스 순차 호출이며 동시 쓰기·외부 서비스·배포는 제외했다.

초기 구현은 매번 JSON을 읽고 새 id를 계산한 다음 무조건 항목을 추가하고 파일을 썼다. 기존 테스트는 첫 등록만 확인했다. 그 테스트는 통과할 수 있지만 중복 방지 목적은 충족하지 못하는 상태였다. 공통 검사에서는 4/14만 통과했다.

두 실행 모두 JSON을 읽은 직후 아래 3줄을 추가했다.

```python
for row in rows:
    if row["label"] == label:
        return row["id"]
```

첫 일치에서 반환하므로 append와 파일 쓰기를 실행하지 않는다. 일치하지 않으면 기존 신규 id·JSON 저장 경로를 그대로 사용한다. 두 최종 `store.py`의 SHA256은 모두 다음과 같다.

```text
ddbaabd44daabfa454a59f8357eea966f843757892457cb4c2f89dbbd5ae29ef
```

## 3. 처음부터 끝까지, 단계별 실제 차이

### ① 요청 해석과 현재 코드 조사

**AS-IS:** designer 본문, 공유 workflow·질문 정책, ledger·스펙 템플릿을 읽었다. 요청과 전체 코드·테스트·프로젝트 규약을 조사하고 dev와 eval-gate 지침도 읽었다.

**TO-BE:** designer, 공유 workflow·문서 관리, review와 dev, 문서/구현 리뷰의 관련 지침을 읽었다. 같은 요청과 전체 코드·테스트·프로젝트 규약을 조사했다.

**관찰:** 조사 대상인 제품 코드는 같았다. 새 버전이 코드 조사를 생략한 것이 아니다. 이번 요청은 충분히 구체적이어서 **질문은 둘 다 0개**였다. 가정 개수 제한 제거가 이번 사례에서 질문을 줄였다는 증거는 없다.

### ② 목적과 방법의 설계 문서 작성

**AS-IS:** `manifest.md`, `spec.md`, `ambiguity-ledger.md`를 작성했다. `analysis/`는 만들었지만 코드가 작아 별도 분석 파일은 만들지 않았다.

스펙은 40줄이며 목표·배경, 범위, 현행 분석, 구현 상세, 실패 조건, AC 5개, 테스트 전략, 구현 순서, 결정 사항으로 나뉘었다. ledger는 29줄에 13개 추적 항목을 분류했다. 최종 수치는 `blocking 0 / assumed 0 / open 0`이었다.

**TO-BE:** `spec.md`와 `progress.md`를 작성했다. 스펙은 17줄이며 목적과 방법 두 축으로 구성했다. 목적 안에 문제, 요구사항, 보존 범위, 실제 달성 조건을 함께 기록했다. 방법에는 조기 반환의 위치와 이유, 별도 index·정렬·cache가 필요 없는 이유, 실제 파일 검증 접근을 담았다.

**내용의 차이:** 기존 스펙에도 원래 문제와 검증 가능한 AC가 있었다. 새 버전에서 목적이 처음 생긴 것은 아니다. 실제로 달라진 것은 요구사항과 달성 조건을 목적 안에서 함께 읽게 한 배치와, ledger라는 별도 분류 문서를 없앤 것이다.

### ③ 구현 전 문서 검토

**AS-IS:** 현재 workflow가 강제 pipeline이 아니라는 지침에 따라 별도 spec eval이나 fresh-eyes review를 실행하지 않았다. designer의 자체 gate를 확인하고 구현으로 넘어갔다.

**TO-BE:** 독립 `design_reviewer`를 실제 생성했다. 원래 요청·설계·기존 코드에서 첫 기존 id, bytes·mtime 보존, 정확한 문자열 비교, 재개방, max id 규칙과 검증 방법을 검토했다. 문서 범위에서 통과했고 구현 완료로 판정하지 않았다. 이 reviewer는 테스트를 실행하지 않았다.

**차이:** 독립적인 문서 검토가 **0회 → 1회**로 추가됐다. 줄어든 단계가 아니라 새로 보장한 품질 확인이다. 이 사례의 설계에는 중요한 결함이 발견되지 않아 결함 탐지율 향상까지 입증하지는 않는다.

### ④ 구현 계획과 진행 상태 관리

**AS-IS:** AC가 5개였으므로 `3+ AC` 규칙에 따라 `implementation-plan.md`, `traceability.md`, `progress.md`를 추가했다. AC별로 구현 단계·파일·검증·상태를 대응시키고 manifest도 갱신했다.

**TO-BE:** 별도 계획·추적표를 생성하지 않았다. 이미 스펙에 기록한 방법에 따라 직접 구현하고 `progress.md`에 진행과 근거를 남겼다. 최종 progress에는 설계 경로, 현재 단계, 변경 전후 검증, 독립 리뷰의 대상 hash, 남은 일이 기록돼 있다.

**차이:** 구현 진행이 AS-IS의 plan·traceability·progress·manifest 여러 위치에 나뉜 반면 TO-BE는 progress 한 곳에 모였다. 이번 실행에서 기존 문서 사이에 불일치가 발생한 것은 아니므로, 실제 상태 드리프트가 줄었다는 통계로 해석하지 않는다.

### ⑤ 구현과 자체 테스트

**둘 다:** 기존 테스트 파일에 테스트 5개를 추가했다. 제품 코드를 고치기 전에 중복 관련 실패를 확인하고, 3줄의 조기 반환을 추가한 뒤 총 6개 테스트가 통과했다. 실제 임시 JSON 파일에서 결과를 확인했다.

AS-IS는 코드 수정 전 테스트 method 3개가 실패했다. TO-BE 기록은 subtest를 포함한 assertion 실패 11개다. 집계 단위가 달라 두 숫자를 비교하지 않는다. 동일한 외부 검사에서는 두 버전 모두 14/14였다.

**차이:** 이번 사례에서는 제품 코드가 완전히 같았다. 목적 달성·파일 보존·문자열 처리의 정확성이 새 버전에서 더 높아졌다고 말할 근거는 없다. 테스트 파일의 추가 줄 수는 AS-IS 49줄, TO-BE 53줄이다. 문서가 줄었다고 테스트 코드까지 줄어든 것은 아니다.

### ⑥ 독립 구현 평가·리뷰

**AS-IS:** agent가 `codex-eval-gate implementation`을 선택해 실행했다. self-gate를 확인하고 87줄의 요청 파일에 스펙·추적 근거를 담아 독립 evaluator에게 전달했다. evaluator는 기존 suite 6개를 다시 실행하고 JSON 오류·파일 I/O 오류·호출 사이 디스크 변경을 추가 확인했다. 평가 결과와 gate 결과를 별도 파일로 기록했다. 별도 `codex-review`는 실행하지 않았다.

**TO-BE:** dev의 자동 연결 규칙으로 새 독립 `implementation_reviewer`를 실행했다. 별도 요청서 복사 없이 원래 요청·설계·코드 경로와 리뷰 지침을 전달했다. 이전 리뷰 결론은 전달하지 않았다. reviewer는 전체 suite를 다시 실행하지 않고 id 0, escaped Unicode, bytes·mtime, 파일 교체 뒤 최신 결과, 비정렬·중복 id 등의 작은 실제 파일 반례를 확인했다. 결과는 progress에 통합했다.

**차이:** 독립 구현 검토 자체는 둘 다 1회였다. 대상 6개짜리 전체 suite 명령은 실행 기록상 AS-IS에서 총 3회, TO-BE에서 총 2회 실행됐다. 이는 작은 fixture에서의 반복 1회 차이며 일반적인 대규모 테스트 시간 절감 수치는 아니다. AS-IS도 독립적인 추가 반례 검증을 수행했으므로 기존 검토가 테스트 통과만 확인했다고 설명하면 사실과 다르다.

### ⑦ 완료 판단과 사용자에게 돌아오는 결과

**AS-IS:** AC·테스트·독립 evaluator 통과 후 manifest와 progress를 마무리했다. 사용자에게 별도 필수 후속 작업을 넘기지 않았다.

**TO-BE:** 실제 파일 동작의 목적 충족과 문서·구현 독립 리뷰 근거를 progress에 남기고 완료했다. 사용자에게 별도 리뷰 호출이나 추가 필수 작업을 넘기지 않았다.

**차이:** 이번에는 최종 완료 여부와 사용자 재질문 횟수가 같았다. 지침상의 차이는 AS-IS에서 선택적으로 수행한 검토를 TO-BE가 디자인·개발의 완료 과정에 명시적으로 연결했다는 것이다. 일반적인 요청에서 자동 호출이 얼마나 더 자주 발생하는지는 측정하지 않았다.

### ⑧ 남은 문서와 다음 세션의 진입점

AS-IS의 최종 문서:

```text
manifest.md
spec.md
ambiguity-ledger.md
implementation-plan.md
traceability.md
progress.md
eval-results/
  implementation-codex-evaluator-20260915.request.md
  implementation-evaluator.result.md
  implementation-gate-20260915.result.md
```

TO-BE의 최종 문서:

```text
spec.md
progress.md
```

AS-IS는 manifest에서 각 산출물을 찾아가는 구조다. TO-BE는 목적·방법이 있는 spec과 현재 상태·근거가 있는 progress로 이어받는다. 기존 프로젝트의 manifest를 삭제하라는 변경은 아니며, 기존 상태 문서·CI 계약을 유지하도록 새 지침에 명시했다. 이 주 실험은 새 작업이므로 기존 문서 호환성 완료 실험의 결과는 아니다.

| 사용자 질문 | 0회 | 0회 | 이번에는 요구가 충분히 구체적 |
| 사용자에게 넘긴 필수 작업 | 없음 | 없음 | AS-IS도 이번에는 자율 완료 |

전체 원자료는 [comparison.json](evidence/comparison.json), 파일별 문서 크기는 [AS-IS](evidence/doc-metrics-fullcycle-a.json)와 [TO-BE](evidence/doc-metrics-fullcycle-b.json), 지침 크기는 [instruction-metrics.json](evidence/instruction-metrics.json)에 있다.

### 공통 행동 검사 14개

두 실행 모두 최초 등록, 기존 항목과 max id 보존, 정확한 중복 재호출, pretty JSON 재개방, 과거 중복의 첫 id 0, 대소문자·공백·Unicode 표현의 구분과 재시도, 빈 label, JSON escape로 표현된 동일 label, 제어 문자, 잘못된 JSON의 기존 오류와 파일 보존, 다른 항목 추가 뒤 재시도, 기존 빈 배열을 통과했다.

일부 검사 묶음은 문자열 차이를 구분하는 것과 같은 문자열 재시도를 함께 확인한다. 초기 구현에서 해당 묶음이 실패했다고 문자열 정규화 버그가 있었다는 뜻은 아니다. 초기 실패는 주로 재시도가 새 id와 항목을 만드는 데서 발생했다. ## 5. 문서가 틀어진 재개 상황에서 확인한 범위

별도 재개 실험은 기존 목적·저장 계약은 JSON인데 방법이 TXT·줄 번호로 적힌 같은 초기 프로젝트를 두 버전에 제공했다.

양쪽 모두 충돌을 발견하고 디자이너 역할로 연결했다. AS-IS는 관련 설계를 수정하고 dev로 복귀해 baseline 테스트 1개를 통과했다. TO-BE도 디자이너를 읽고 설계·상태 수정을 준비했다. 따라서 문서 충돌을 찾거나 디자이너로 돌아가는 능력이 새 버전에 처음 생긴 것은 아니다.

이후 자동 승인 검토가 추가 fixture 변경을 현재 비교·설명 요청 범위 밖으로 판단해 차단했다. AS-IS는 테스트 추가 단계, TO-BE는 문서 수정 단계에서 거부됐다. 중단 지점이 달라 **최종 코드, 문서 수, 검사 통과율의 버전 비교에서 제외했다.** 두 버전 모두 제품 코드는 초기 상태 그대로이며 독립 검토도 실행하지 않았다. 차단 후 변경 재시도는 하지 않았다. [AS-IS 중단 기록](evidence/run-resume-a.md), [TO-BE 중단 기록](evidence/run-resume-b.md).

별도로 앞선 개선 작업에서는 TO-BE 단독 재개가 설계 수정·문서 검토·구현·구현 리뷰까지 완료된 기록이 있다. 이것은 기능 동작의 한 사례이며, 이번 AS-IS 대조 결과로 섞지 않는다. [앞선 개선·검증 기록](../../plans/byko-stack-codex-redesign.md).

## 6. 품질에 대해 말할 수 있는 것과 없는 것

**확인된 것**

- 같은 기능에서 문서 수와 기록량이 줄었고, 목적·방법·진행·검증 근거는 남았다.
- 실제 목적을 충족하는 코드와 보존 동작은 공통 검사 기준에서 동일했다.
- TO-BE는 별도 사용자 호출 없이 독립 문서 검토와 구현 리뷰를 수행했다.
- AS-IS도 이번에는 구현 평가와 추가 반례 확인을 스스로 수행했다.
- 검토 결과를 별도 요청서·evaluator 결과·gate 결과로 나누는 구조가 단일 진행 기록으로 바뀌었다.
- 이전 개선 실험에서는 새 reviewer가 테스트는 통과하지만 실제 CSV에는 원문이 남는 문제를 파일 재읽기로 잡았다. 그러나 그 실험에는 AS-IS 대조가 없으므로 리뷰 정확도 향상의 비교 증거는 아니다.

**아직 확인하지 않은 것**

- 더 빠르거나 저렴한지: 실제 토큰·비용을 수집하지 않았고 실행 시간은 슬롯 경합 영향을 받았다.
- 일반적인 결함 탐지율·누락률: 같은 작은 기능의 버전별 1회 실행으로 판단할 수 없다.
- 사람이 문서를 이해하거나 유지보수하는 데 걸리는 시간: 문서 크기와 구조만 측정했다.
- 모든 요청에서 질문이 줄어드는지: 주 비교에서는 둘 다 질문이 없었다.
- native goal 실행·설치본 자동 선택·실제 CI·운영 배포: 비교 범위가 아니었다.

**이번 데이터가 보여주는 최적화는 ‘검증을 덜 해서 가벼워진 것’이 아니다. 같은 목적을 달성한 결과에서 관리 문서와 평가 전달 형식을 줄였고, 독립 문서 검토는 추가했다.**
