# byko-stack-codex 0.6 — 변경과 검증

2026-10-31. 일반 이슈·알람·개발 요청을 명시적인 기본 경로로 연결하고, 목표·합의와 원자료를 판단·인계·재개에 사용하도록 개선했다. 구조 검사·독립 변경 검토와 실제 행동 평가의 확인 범위를 구분한다.

## 목적과 변경

| 관점 | 이루려는 결과 |
|---|---|
| 누가 | 업무를 맡기는 사용자, 이를 수행하는 Codex 메인과 작업자 |
| 언제 | 기능 개발·고도화, 문제 진단·수정, 재개·인계, 알려진 플레이북 밖 요청을 받았을 때 |
| 어디서 | 리포별 하네스와 실행 환경이 다른 코드베이스 및 연결된 자료·서비스 |
| 무엇을 | 요청한 결과까지 목표를 유지하며 조사·설계·구현·검증을 연결하고 실제 근거로 완료를 판단 |
| 어떻게 | 기본 경로와 역할·반환을 명시하고 근거에 따라 축소·보완. 공유 자료를 갱신하며 중요한 전제와 관련 대상을 확인 |
| 왜 | 사용자가 흐름 단절·성급한 축소·예시 과적합·부분 맥락의 누락을 매번 교정하는 부담을 줄이기 위해 |

- 일반 진입은 `byko-work`, 설계 조율은 `byko-design`, 독립 검토 조율은 `byko-review`다. 구명칭은 각각 `codex-spec-dev`, `codex-spec-designer`, `codex-review`였다. 중복 발견을 만드는 구명칭 wrapper는 유지하지 않는다.
- 기존 전문 스킬 6개를 보존하고 후보 작성만 맡는 `byko-propose`와 설계자 역할을 추가했다. 전문 작업자는 전체 조율을 역호출하지 않는다. 총 스킬 10개·역할 5개다.
- 진단·변경·미정형 플레이북과 병렬 조사·반증·후보 비교·다중 검토·분리 구현의 입력·반환·인수·복귀를 연결했다. 모든 경우에 고정 팀이나 대안 수를 강제하지 않는다.
- 대목표·유효한 합의·보존 기준을 계속 대조한다. 새 피드백은 예시·추가·부분 정정·취소를 구분해 영향받은 판단만 갱신한다.
- 코드·정책·컨벤션·데이터 자체·데이터 흐름은 조사 관점의 예다. 결론이 의존하는 리포·인프라·외부 근거도 허용된 범위에서 확인하며, 초기 인상만으로 축소하지 않는다.
- 기존 자료를 공유·갱신한다. 새 지속 작업은 `docs/work/<작업>/index.md`에서 시작하고 독립적으로 읽거나 갱신할 이유가 있을 때만 분리한다. 기존 작업 문서를 자동 이관하거나 단독 조회에 문서세트를 만들지 않는다.
- 검증 경로는 리포의 기존 방법을 먼저 확인하고 부족한 방법만 보완한 뒤 실제 실행한다. 사용자용 뷰는 주제별 의미 있는 시각 표현을 요구하며 동영상·인터랙션 등 표현 선택을 보존한다.

## 설계 비교와 근거

같은 대목표·사전 기준으로 두 후보를 독립 작성하고 별도 검토자가 비교했다. 두 후보는 일반 진입+재사용 능력으로 수렴했다. 후보 작성과 전체 설계 조율을 분리해 재귀 위험을 줄이는 B를 기반으로 선택했다. 성능상 최적임을 입증한 것이 아니라 목표·실행 경계와 변경 비용을 대조한 설계 선택이다.

기존 0.5.0에도 육하원칙·독립 검토·문서 재사용이 있었다. 이를 없는 기능처럼 설명하거나 대체하지 않고 요청 진입과 실제 수행 연결을 보완했다. 참고한 [pstack 0.15.36](https://github.com/cursor/plugins/tree/4dd1d05818d19792e7cd6e818f1667f95f7e1dbe/pstack)의 기본 경로·반환·복귀와 미정형 작업 구성, [Claude dynamic workflows](https://claude.dev/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code/)의 독립 후보·반증·종합을 활용했다. 고정 인원·불확실하면 단순 경로·재현 성공 강제·포괄 외부 권한·전용 실행기를 복제하지 않았다.

Codex 연결은 [skills](https://learn.chatgpt.com/docs/build-skills), [subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents), 실제 CLI 0.166.0과 해당 프로토콜로 확인했다. description의 암묵 호출은 강제 hook이 아니며 TOML helper는 실행·등록·권한 강제가 아니다.

## 검증 조건과 현재 결과

변경 전 패키지는 `85c0c5f`의 0.5.0, 후보는 평가 시작 시 파일별 SHA-256으로 동결했다. CLI root 모델은 `gpt-6.1-sol`, reasoning `high`를 요청했다. 개인 설정·plugins·memories를 끄고 별도 임시 workspace의 `.agents/skills`로 로컬 스킬을 노출했다. 사용자 요청은 스킬명을 지정하지 않고 로컬 byko stack으로 `REQUEST.md`를 처리하도록 했다. **로컬 스킬 발견 평가이며 marketplace 설치 후 전체 실행과는 다르다.** 글로벌 AGENTS와 실행 환경의 기본 지침은 여전히 적용되므로 순수 플러그인만의 효과로 해석하지 않는다.

| 확인 | 결과와 경계 |
|---|---|
| 패키지·helper 자동 검사 | unittest 9개 통과. 설치 위치 이동, 역할 설정, 누락 파일·외부 symlink·잘못된 TOML 거절, 스킬 이름·메타데이터·내부 링크 확인 |
| YAML·변경 검사 | Ruby YAML.safe_load로 frontmatter·메타데이터 파싱, git diff --check 통과 |
| Codex 실제 패키지 파싱 | `plugin/read`가 로컬 버전 0.6.0과 새 이름의 스킬 10개를 반환. install/refresh는 수행하지 않았으며 기존 전역 설치본 교체를 뜻하지 않음 |
| 진단 — 변경 전/후 | 같은 송수신 fixture에서 실패 시도 3건을 최종 고객 실패 3건으로 오판하지 않음. 원인·회복·미확인 구별, 코드·데이터 무수정 확인 |
| 부분 맥락에서 재개 | 기존 목표·분석·접수 기록을 읽고 기존 analysis/index만 갱신. ‘실패 횟수 표’ 예시가 원인·영향 목적을 지우지 않음 |
| 미정형 비교 | 보존 기간·저장 예산으로 설정 B를 선택하고 복원 속도 미확인을 유지. 설정 적용·무관한 조건 추가 없음 |
| 공개 프로젝트 기능 개발 | 변경 전/후 모두 외부 기능·보존 계약 6개 확인 통과. 후보의 구현 전 실패→구현→unittest 16개·doctest 136개 통과와 기본 동작 21,504회 비교를 기록에서 확인. 작업 문서는 한 index를 갱신 |
| 독립 작업자 실행 추가 확인 | 원세션에서 새 컨텍스트 reviewer 생성 호출·성공 응답·최종 반환 원문 수신 확인. 내용은 진단 원자료 및 메인 결론과 일치. 최초 전달 본문은 호스트 암호화로, child 내부 도구 실행은 로그 부재로 미확인 |
| 설계 전용 요청 | 단일 프로세스 작업큐의 영속화 대안·조건부 권고·검증 계획 작성. 실제 API 의미와 저장 실패·복구를 반영하고 원본 요청·제품 코드 무수정, index 하나 갱신을 독립 대조. 이 실행의 후보 생성·반환 원문은 JSONL에 없어 해당 오케스트레이션 내부 절차는 미검증 |

진단·재개·비교·Feature의 내용·보존·자료 갱신은 별도 검토자가 로그와 실제 파일을 대조했다. 기존 버전도 진단과 기능 결과가 맞았으므로 정확도·일반 성공률의 향상을 주장하지 않는다. 최초 CLI JSONL에는 spawn·반환 원문이 빠져 독립 검토 자기보고를 확정할 수 없었다. 원세션 기록을 보존하는 추가 진단 실행에서 생성과 반환을 확인했다. 종료 후 새 turn의 목록 조회에서는 이전 작업자가 보이지 않았으므로 실제 저장된 원세션 근거를 사용했다. 전달 기준·child의 실제 조회까지 검증한 완전한 독립 절차 평가로 확대하지 않는다.

설계 전용 사례도 별도 검토자가 요청·현행 코드·최종 설계를 대조해 내용·범위 통과로 판단했다. 후보들은 단일 프로세스·로컬 디스크 조건에서 비교됐으며 직렬화·외부 객체 변경·성능 가정을 미확정으로 남겼다. SQLite 같은 해당 사례의 선택을 플러그인 기본 정책으로 옮기지 않았다. 패키지 구현과 후속 문구·보고서의 독립 검토도 통과했다. 새 View 기준의 실제 사용자 이해도, 모든 리포·호스트, 자동 compaction, 다중 writer 실패 복구는 이번 행동 평가로 입증하지 않았다.

후보 평가 후 native goal 사용의 명시적 요청 경계를 분명히 하고 한국어 조사·‘끝점’ 표현을 고쳤다. 동결된 최초 평가본과 이 후속 수정본을 구분한다. 추가 진단 trace는 당시 현재 작업본에서 실행했다. 최종 구조 검사는 후속 수정본에서 통과했으며, 모든 최초 사례를 최종본으로 반복한 것은 아니다.

## 공개 프로젝트와 재현 가능한 기능 기준

[boltons](https://github.com/mahmoud/boltons) commit `d31d821d56c8f7756af9c30a864077f2e5855321`을 사용했다. 조회 당시 약 6.9k stars의 표준 라이브러리 기반 Python 프로젝트다. 선택한 `iterutils`와 의존 모듈·프로젝트 설정을 읽고 별도 사본에서 작업했다. 설치 스크립트·네트워크·운영 자원을 실행하지 않았고 소스의 일부 실행 범위를 점검한 것이지 저장소 전체의 보안 인증은 아니다.

요청: `chunked`와 `chunked_iter`에 `strict=True`를 추가해 소비한 마지막 청크가 짧으면 ValueError. 기본 동작·fill·str·bytes·generator·count를 보존하고 strict+fill은 거절한다. 구현·테스트·문서까지 로컬에서 완성하되 외부 게시·커밋·푸시·배포는 제외했다.

독립 확인 기준은 구현 전에 작성했다: 빈 입력·정확한 배수, 마지막 잔여의 지연 오류, 기본/False의 부분 청크 보존, fill 충돌, str/bytes·count 소비 경계, 기존 잘못된 size·알 수 없는 키워드 오류. 두 결과물을 같은 기준으로 확인했다. 초기 소스에서는 strict 미지원으로 실패했다. 전체 pytest·모든 Python 버전·Sphinx 빌드는 평가 범위 밖이다.

진단 fixture는 시도 로그·수신 기록·정책·송수신 코드·관찰 종료를 분리했다. e1은 재시도 접수, e2는 timeout 시 이미 접수돼 재시도 중복 제거, e3는 관찰 종료 이후 재시도 예정이었다. 원인 내부 로그와 후속 고객 업무 완료는 제공하지 않아 미확인으로 남겨야 한다. 재개 사례는 송신 요약만 주되 기존 문서·원자료에 접근 가능하게 했다. 이는 자동 compaction 자체의 재현이 아니라 부분 컨텍스트 인계 시험이다.

## 유지보수 확인

```sh
python3 -m unittest discover -s plugins/byko-stack-codex/tests -v
git diff --check
```

형식·링크 검사는 모델의 실행을 보장하지 않는다. 자연어 진입·부분 인계·유효한 정정·연결된 근거·작은 작업의 비례성은 실제 요청으로 재평가해야 한다. 공개 사례이며 holdout이나 통계적 품질 평가가 아니다. 독립 컨텍스트는 파일 접근 격리를 의미하지 않는다.
