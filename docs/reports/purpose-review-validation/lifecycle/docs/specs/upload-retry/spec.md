# 파일 접수 재전송

## 목적

단일 서버에서 순차적으로 `accept`를 호출하는 고객은 응답을 다시 받기 위해 같은 접수를 재전송할 수 있다. 고객별 `request_id`와 bytes 내용이 같은 시도는 기존 접수 ID를 받고 추가 저장이나 후속 처리를 만들지 않아야 한다. 같은 고객·요청 ID로 다른 내용을 보내면 오류가 발생하고 기존 접수는 그대로 보존되어야 한다.

근거는 `REQUEST.md`, `CONTRACT.md`, `README.md`다. 파일명은 표시용이며 같은 파일명을 가진 다른 요청은 별도 접수다. 다른 고객은 같은 요청 ID를 사용할 수 있다. 공개 함수 시그니처와 기존 `records` 필드(`id`, `customer_id`, `request_id`, `filename`, `content`)는 유지한다. UI와 다중 프로세스는 범위 밖이다.

달성 조건은 실제 공개 함수 호출에서 반환 ID·오류와 `records`의 값 및 append 횟수가 아래 기준과 일치하는 것이다. 이 프로젝트에는 외부 저장소나 후속 처리 경로가 없으므로 records append가 저장 경계다.

## 구현 전 검토 기준

아래 기대값은 CONTRACT.md에서 도출했다. 기준 작성 시 원본 `uploads.py` SHA-256은 `c2b1a2ccb70b5f2def93ed88e92eaeab7ded78cd3dd201718d8248fe1f1b7ff7`이다.

| 조건 | 기대 결과 | 관찰 방법 |
|---|---|---|
| 첫 접수 | 기존 필드와 전달값을 저장하고 ID 반환 | 반환값, records 값, append 횟수 |
| 같은 고객·요청 ID·bytes 재전송 | 기존 ID, 저장 내용 및 append 횟수 불변 | 복사한 상태와 대조 |
| 재전송에서 표시용 파일명만 변경 | 기존 ID와 기존 파일명 보존 | 반환값과 records 대조 |
| 같은 고객·요청 ID, 다른 bytes | 오류, 기존 상태와 append 횟수 불변 | 예외 및 상태 대조 |
| 같은 고객, 다른 요청 ID, 같은 파일명 | 별도 접수 | 서로 다른 ID와 두 레코드 |
| 다른 고객, 같은 요청 ID | 각각 접수 | 고객별 저장 및 각 재전송 |
| 기존 records로 재시작된 호출 | 기존 ID 재사용, 동일 충돌 규칙 | 미리 채운 records 호출 |
| 빈 bytes, 여러 접수 사이의 이전 요청 재전송 | 동일한 재전송·충돌 규칙 | 공개 함수로 순차 실행 |

충돌 오류의 구체적인 Python 형태는 원문에 없다. 호출자가 오류를 관찰할 수 있는 `ValueError`를 선택할 예정이며 정책 요구로 간주하지 않는다. 입력은 계약에 제시된 bytes이며 bytes 이외 형식의 강제 변환·검증 정책은 추가하지 않는다. 외부 후속 처리나 비순차 호출은 확인 대상이 아니다.

## 방법

현행 공개 진입점은 `uploads.py:accept` 하나이며 외부 DB·서비스·후속 처리 호출은 없다. 현재는 매 호출마다 `len(records) + 1` ID를 부여해 append하므로 재전송과 내용 충돌을 모두 신규 접수한다.

기존 `records`를 순서대로 확인해 `customer_id`, `request_id`가 모두 같은 레코드를 찾는다. 찾은 레코드의 `content`를 입력 bytes와 비교해 같으면 그 레코드의 `id`를 즉시 반환하고, 다르면 `ValueError`를 발생시킨다. 두 분기 모두 레코드와 목록을 수정하지 않는다. 일치하는 요청이 없는 경우에만 기존 신규 접수 경로를 실행한다. 이로써 기존 목록만으로 중복을 판단하므로 숨은 전역 캐시나 저장 필드 추가가 필요 없고, 순차 호출 계약하에서는 별도 잠금이 필요 없다. 기존 ID 생성 방식과 다섯 필드는 유지한다.

검증은 표준 라이브러리 `unittest`로 공개 `accept`를 직접 호출한다. append 횟수를 기록하는 목록으로 저장 호출 횟수까지 관찰하고, 호출 전 깊은 복사와 비교해 충돌·재전송의 전체 상태 보존을 확인한다. 같은 내용이라도 다른 요청이면 새 접수임을 검증하고, 미리 채운 기존 레코드의 ID를 그대로 반환하는지 확인한다. 기존 원본의 빈 목록 신규 접수와 시그니처·필드 계약도 검증한다. README에는 충돌 예외와 실행 명령을 기록한다.

잘못된 기존 레코드, 외부에서 목록을 수정하는 경우, bytes 외 입력의 정책은 원문에서 정하지 않았다. 이 변경에서는 별도 지원·복구 정책을 만들지 않는다. 이 제한은 명시된 재전송 계약을 축소하지 않는다.
