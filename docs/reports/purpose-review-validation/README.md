# Codex Stack 0.5 작업 준비·검토 검증

0.5 후보의 목표·계획·구현 검토 연결을 구현했고, 0.4와 같은 공개 입력의 새 컨텍스트 비교에서 기존 판단을 보존했다. 0.4도 이 사례에서는 요청 범위를 지키고 결함/정상 결과를 구분했다. 이번 결과를 일반적인 결함 탐지율 향상이나 사용자 개입 감소로 해석하지 않는다.

## 대상과 방식

- 시작 checkout: `fix/byko-stack-0.3.1-code-explorer`, HEAD `8e3185f410a509e3cfaec2386e4f7a412c1d02f2`. Codex Stack은 0.4.0이며 `a643b7c` 대비 소스 차이가 없었다. Claude Stack의 동시 변경과 기존 PNG 자료는 이번 수정 대상이 아니다.
- [설계와 사전 기준](../../specs/purpose-review/spec.md), [실행 전 평가 계획](../../specs/purpose-review/evaluation-plan.md).
- 변경 전 패키지를 임시 경로에 복사하고 읽기 전용으로 고정했다. [기준선·입력 hash](baseline-manifest.json), [최초 후보 hash](candidate-manifest.json), [후속 수정 후보 hash](candidate-v2-manifest.json).
- G/P/C 각각 버전별 새 agent 컨텍스트로 1회 수행. [세션 기록](runs.json)의 설정은 모두 `gpt-6.1-sol/high`. 실행자에게 이전 결과·기대 판정·다른 버전을 주지 않았다. 도구 생성 응답은 실제 모델을 표시하지 않았고, 이후 로컬 세션 설정 기록을 확인한 것이다.
- 최초 비교 후보와 최종 후보 v2의 차이는 `codex-spec-dev`의 기존 설계 검토 이력 확인 문단뿐이다. G/P/C가 호출한 전문 스킬과 지침은 동일하다. 추가 분기는 R1/R2로 구분한다.

G 비교는 위임이 없는 읽기 전용 환경으로 목적 작성만 확인했다. 자동 독립 검토 연결의 증거로 사용하지 않는다. 양쪽 모두 독립 검토가 없음을 밝혔다. 코드/계획 비교는 이미 독립 reviewer이므로 재귀 생성 없이 직접 수행했다.

## 전체 연결 실행

별도 [lifecycle](lifecycle)에서 스펙이 없는 파일 접수 재전송 구현 요청을 수행했다. 목표·사전 기준 작성 → 독립 목표 검토 → 방법 보완 → 계획 검토 → 구현 → 자체 테스트 → 독립 구현 검토를 이어갔다. 코드가 변경되기 전의 기준·코드 상태를 [중간 관찰](lifecycle-during-design.json)로 보존했다.

- 작은 조사·구현은 메인이 직접 수행하고 필요한 reviewer만 생성했다. 고정된 두 페르소나나 전체 팀을 만들지 않았다.
- 목표/계획의 별도 판단을 같은 독립 reviewer thread에서 이어갔다. 이를 매번 새 컨텍스트에서 수행한 평가라고 주장하지 않는다. 작성자의 전체 대화는 전달하지 않았다.
- 계획 리뷰의 필드 수 오기를 원본과 대조해 정정했다. 제품 정책이나 동작을 바꾸는 blocking 반려는 이 fixture에서 나오지 않았다.
- 공개 함수 테스트 7개(subtest 포함) 통과. reviewer는 별도 메모리 사례로 bytes 구분, 충돌 상태 보존, 고객 분리 등을 확인하고 구현 검토 통과를 반환했다. 동일 전체 suite의 재실행은 하지 않았다.
- 결과·근거·남은 범위는 [진행 기록](lifecycle/docs/specs/upload-retry/progress.md)에 있다. 외부 DB·운영 배포가 없는 작은 함수 프로젝트의 실제 경계에 한정한다.

## 독립 패키지 리뷰와 수정

설계 리뷰는 통과했다(spec SHA-256 `d0e7d8cdee7c1dedaa01bc567eb57274b5bae8effc7decb66357a7c74653d556`). 변경 리뷰는 기존 설계가 충분하지만 검토 이력이 없는 개발 진입에서 목표·계획 리뷰를 건너뛸 수 있는 연결 공백을 지적했다. `codex-spec-dev`에서 현재 요청·버전에 유효한 검토 근거를 확인하고 없거나 무효한 범위만 구현 전 리뷰하도록 수정했다. 기존 문서 재작성과 유효한 리뷰 반복은 요구하지 않는다.

동일 finding의 정적 재검토는 통과했다. 수정 파일 SHA-256은 `91169faff43395a049481a91ee3156eb91ff8a58665455ea386ad25b645901b5`다. 이는 변경 전 모델이 반드시 해당 리뷰를 생략한다는 재현 결과가 아니며, 지침상 누락된 분기를 보완한 것이다.

추가 실행 R1은 통과했다. [기존 설계 재개](resume)에서 제품 수정 전에 독립 목표·계획 검토를 수행했고, 충분한 `docs/spec.md`는 바이트까지 유지했다. 기존 `docs/progress.md`에 근거를 이어 썼고 새 상태 경로는 만들지 않았다. 구현 테스트 8개와 별도 구현 reviewer의 추가 실행이 통과했다. 실제 호출 순서와 reviewer 반환은 [workflow-events.json](workflow-events.json), 원문 응답은 [runs.json](runs.json)에서 확인할 수 있다. 중간 파일 관찰 시점에는 이미 구현이 시작되어 있었으므로 `resume-during-review.json`을 구현 전 상태의 증거로 쓰지 않는다.

R2도 통과했다. 완료된 동일 작업을 새 컨텍스트에서 다시 요청했을 때 현재 요청·파일 hash와 기존 검토 근거를 대조해 목표·계획·구현 리뷰를 재사용했고, 제품 코드와 테스트를 변경하지 않았다. 설계에 남은 구현 전 상태의 현재형 설명을 과거 배경과 현재 구현으로 구분하고 해당 문서 변경만 새 독립 reviewer에게 검토받았다. [재진입 결과](resume-reentry), [재진입 전후 hash](resume-reentry-changes.json)에 기록했다. 단, 기존 8개 테스트를 다시 실행했으므로 불필요한 반복 작업까지 제거했다는 증거로 사용하지 않는다. R1의 원본 결과는 별도 보존했다.

## 형식·패키지 검증

- helper unittest 6개 통과. helper·모델·effort·설정 schema는 변경하지 않았다.
- 9개 스킬 `quick_validate.py`, UI YAML과 스킬 이름 참조·설명 길이 검사 통과.
- JSON/TOML 파싱 및 패키지 내부 Markdown 상대 링크 확인 통과.
- `git diff --check`는 이번 소스·README 범위에서 통과.
- 기본 Python에는 PyYAML이 없어 첫 validator 실행이 실패했다. 기존 uv 캐시의 PyYAML을 `PYTHONPATH`로 제공해 통과했으며 전역 환경은 수정하지 않았다.

## 확인하지 않은 범위

공개된 소수 fixture이며 holdout·일반 성공률·비용/시간 개선 측정이 아니다. 다양한 문제에서 여러 조사 관점을 선택하는 품질, 분석 agent의 blocking 반려·재조사 반복, 실제 사용자 개입 감소는 아직 입증하지 않았다. 직접 스킬 경로를 지정한 실행이며 설치 후 자동 선택, 현재 사용자 설치 캐시 갱신·새 세션 발견, native agent 등록과 공개 배포도 확인하지 않았다. 실제 화면 검증은 이번 변경 대상이 아니다.
