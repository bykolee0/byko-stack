# Stack 역할·스킬 통합 검증

통합 검증일: 2026-10-01. 아래 설치·실행 결과와 hash는 `byko-stack-codex` 0.4.0의 당시 작업 파일을 대상으로 한다. 이후 뷰어 지침 변경은 마지막 절에서 별도로 검증하며 이전 설치본과 동일하다고 간주하지 않는다. [설계](../specs/stack-agent-integration/spec.md)와 [현재 진행 상태](../specs/stack-agent-integration/progress.md)를 기준으로 검증한다. 이전 역할 단독 검증은 [기존 기록](byko-reusable-agents-validation.md)에 보존한다.

## 패키지와 설정

- Codex CLI `0.159.3`의 임시 설정 디렉터리에서 로컬 marketplace 등록, `plugin add byko-stack-codex@byko-integration-test`, `plugin list --json`을 실행했다. 0.4.0 설치 및 활성화가 확인됐다. 개인 Codex 설정·기존 설치는 변경하지 않았다.
- 실제 설치 캐시에 역할 TOML 4개와 `SKILL.md` 9개가 포함됐다. 임시 marketplace 원본 디렉터리를 옮긴 후에도 설치 캐시의 helper로 네 역할을 준비했다. 모두 `gpt-6.1-sol` / `high`와 설치 캐시 내부 전문 스킬 경로를 반환했다. 별도 Git checkout이나 형제 플러그인은 사용하지 않았다.
- 소스와 설치 캐시의 파일 33개를 경로별 SHA-256으로 비교해 동일함을 확인했다. `__pycache__`를 제외한 상대경로→hash JSON을 key 정렬해 직렬화한 digest는 `0e7b4c79d4ddc400de08a06ec2ef79679c2f66ef28f4033edaff17577251794b`다. 원본 목록은 임시 루트의 `package-sha256.json`에 있다.
- 이 결과는 **설치된 파일에 접근할 수 있다는 검증**이다. native custom agent 자동 등록·UI 노출이나 모델 실행을 CLI 설치 결과로 간주하지 않는다.
- 임시 검증 루트: `/private/tmp/byko-stack-integration-_g9g5v92`. 설치 결과는 `install.stdout.json`, 활성 상태는 `list.stdout.json`, 역할별 출력은 `byko-*.prepared.json`이다. 임시 파일은 정리될 수 있으므로 이 문서에는 결과와 재현 방법을 남긴다.

## 형식과 helper

- `skill-creator/scripts/quick_validate.py`로 스킬 9개 통과. UI prompt의 스킬 이름, 자동 선택 정책, TOML 필드·모델·effort, manifest와 패키지 내부 Markdown 상대 참조도 확인했다.
- `python3 -B -m unittest discover -s plugins/byko-stack-codex/tests -v`: 6개 테스트 통과. 이동된 패키지·공백 포함 경로, 네 역할의 실제 설정 읽기, 설정 변경 반영, 알 수 없는 역할·누락된 스킬·외부 symlink·잘못된 TOML·지원하지 않는 설정의 실패 처리를 검증했다.
- `git diff --check` 통과. 현재 환경에 예전 `plugin-creator`·`validate_plugin.py`가 없어 공식 패키지 규격과 실제 CLI 설치로 보완했다.

## 실행 및 독립 검토

- `integration_design_review`: 통합 설계 검토 통과. 대상 spec SHA-256 `7e8d22866a1568efe0b4758bd335c3245cf226ad9feb0bde89703ce82fb2291c`.
- `integration_implementation_review`: 패키지 정적 구현·문서 검토 통과, 수정이 필요한 실제 결함이나 회귀를 발견하지 못했다. 원래 요청·설계와 현재 소스를 읽었고 다른 실행자의 fixture·이전 리뷰는 보지 않았다. helper SHA-256 `96b499abdcd752af7b3b493ead53dc3f7b7c009fd0908e6949428b56a4d68e6b`. 이 판정은 실제 실행·화면 검증까지 포함하지 않는다.
- 독립 실행 controller는 설치본에서 reviewer 설정과 지침을 읽고 `gpt-6.1-sol` / `high`, 새 컨텍스트로 생성을 요청했으나 `agent thread limit reached`를 받았다. 현재 환경에서는 완료된 thread도 한도에 포함됐다. 반복 생성·외부 프로세스로 우회하지 않고, 해당 fixture의 구현 대화나 예상 결론을 보지 않은 기존 검토 thread를 재사용했다. 각 thread의 최초 생성 요청은 `gpt-6.1-sol` / `high`였다. **한도 상황에서의 새 생성 성공은 검증하지 못했으며, 재사용 진행에는 메인의 개입이 있었다.**

### 실제 작업 시나리오

| 시나리오 | 관찰한 결과 |
|---|---|
| 스펙 없는 작은 개발 요청 | 설치된 `codex-spec-dev`가 설계·단일 진행 상태를 만들고 문서 검토 후 `byko-implement`를 직접 적용했다. 모든 작업에 분석가·구현자 생성을 강제하지 않았다. |
| 중복 등록 구현·검증 | 정확히 같은 label에는 기존 ID를 반환하고 파일 bytes·mtime을 보존했다. 새 ID 최댓값 + 1, 문자열 구분, 기존 JSON 형식, 읽기·파싱 오류 전파를 포함한 테스트 9개가 한 번에 통과했다. |
| 자동 구현 리뷰 | 설계 reviewer와 별도의 구현 reviewer를 사용했다. 구현 reviewer에게 이전 판정·작성 대화·진행 문서를 전달하지 않았다. 추가로 임시 파일의 쓰기 금지, bytes·mtime, 큰 ID, Unicode 구분, 추가 필드 보존을 확인해 통과했다. 중요한 finding이 없어 수정·재검토 분기는 이번 시나리오에서 실행되지 않았다. |
| 코드만 분석 | 설치본 분석가 역할을 별도 후속 작업에 적용했다. `service.py`와 허용된 로컬 지침만 읽고 소스 사실·표준 라이브러리 해석·미확인을 구분해 Markdown 응답으로 반환했다. 문서·데이터·외부 시스템 조사, 파일 저장, 추가 agent 호출로 확대하지 않았다. |
| 기존 작업에서 설계만 재개 | 설치본 `codex-spec-designer`로 기존 `docs/feature/design.md`와 상태 원본 `manifest.md`만 수정했다. 다른 경로의 spec·progress를 새로 만들지 않았다. 기존 덮어쓰기 설계를 파일 보존·`FileExistsError` 설계로 바꾸고 후속 구현 영향을 남겼다. 제품 코드와 무관한 데이터의 변경 전후 hash가 동일했다. |
| 위임이 허용되지 않는 상황 | 위 설계 재개 요청에서 신규 agent·기존 agent 위임·외부 모델 호출을 금지했다. 직접 가능한 문서 검토는 수행하되 판정을 `미검증`으로 남겼다. 이전 완료 표시를 새 설계의 독립 검토 통과로 재사용하지 않고 재개 지점을 기록했다. |

실행 fixture는 임시 루트의 `fixture/`다. 구현 결과 `store.py` SHA-256은 `61205efcda1bd5c7d427589622cce7977ced76aa0ab312184e81f9fe9f29de5e`이며, 테스트·리뷰 근거는 fixture의 `docs/specs/register-idempotency/progress.md`에 기록했다. 설계 재개 fixture는 `design-resume/`이고 변경된 설계 hash는 `b91f033b352f6dae2906f049e8a7cc449cdbce4faf2f16430bfec817430c9ab0`이다. 실제 동작 검증은 이 작은 파일 저장 시나리오에 한정한다. 임의의 프로젝트에서 동일한 품질이나 위임 선택을 보장하는 결과는 아니다.

## 검증 경계

- 역할 모델·노력 수준은 생성 도구의 실제 인자에 전달한다. 생성 도구가 적용된 모델·effort를 반환하지 않는 경우에는 **요청 설정 확인**까지만 보고한다.
- 이전 뷰어 검증에서 실제 브라우저 접근이 차단됐다. 해당 접근을 다른 경로·서버로 우회하지 않았다. HTML 정적 구조·내용·상태 검증과 실제 화면·탐색 UX는 다르며, 이번 통합 검증은 실제 화면 확인을 완료했다고 주장하지 않는다.
- 사용자 전역 native 역할 등록, 기존 개인 플러그인 업데이트, Git commit·push·공개 배포는 수행하지 않았다.

## 2026-10-02: HTML / View 공통 원칙 반영

사용자가 제공한 14개 원칙과 기존 지침을 비교했다. 뷰어 역할의 목적은 사람의 이해·탐색을 책임지는 제작이며, `byko-build-viewer`는 그 방법을, `byko-review-viewer`는 독자가 실제로 이해·탐색할 수 있는지의 판단 기준을 담당한다. 이 책임 분리는 유지했다. 숫자 해석, 시각적 정보 계층, 검색, 출처 메타데이터 분리 등은 기존 내용만으로 충분히 명시되지 않아 보완했다.

| 사용자 원칙 | 기존 상태 | 반영한 제작 기준 |
|---|---|---|
| 목적 | 사람의 이해·판단 목적 있음 | 조사·분석을 빠른 이해와 머릿속 연결을 위한 뷰로 재구성 |
| 사람 우선 | 원문 꾸미기 지양, 구조 복사 금지는 암묵적 | 데이터 구조·조사 순서·원장 대신 독자의 이해 순서 사용 |
| 스토리 우선 | 전체·세부와 인과 연결 있음 | 화면 제작 전에 이해 순서와 관계 설계 |
| 시각화 우선 | 관계도·흐름·비교·차트 중심 | 시간·규모 등 정보 성질과 다양한 표현 수단 중 적합한 것 선택 |
| 장식 금지 | 카드 개수로 품질 판단 금지 | 동일 카드·화살표·레이아웃의 일률적 반복도 금지 |
| 숫자도 번역 | 수치에 적절한 차트만 언급 | 단위·기간·비교 기준·증감·규모, 필요 시 환산·절대값과 증가율 |
| 사람의 언어 | 배경·내부 코드명 설명 있음 | 직역·약어와 정식 용어보다 쉬운 역할·실제 의미를 먼저 설명 |
| 문맥 안에서 설명 | 필요한 용어를 제때 설명 | 제품·서비스·재무지표도 현재 위치에서 외부 검색 없이 이해 |
| 데이터 보존의 의미 | 사실·조건·불확실성 보존 있음 | 중요한 수치·반론·한계까지 적절한 표현에 보존, 원문 복사와 구별 |
| 정보 계층 | 요약에서 세부 이동 있음 | 핵심 이야기→중요 근거→세부→전체 원자료와 시각적 무게 구분 |
| 탐색 가능성 | 목차·현재 위치·복귀·작은 화면 있음 | 긴 뷰의 검색·앞뒤 이동·모바일 탐색까지 명시 |
| 근거 분리 | 근거 확인만 언급 | 주장 가까이 근거를 두고 긴 출처 메타데이터는 상세로 분리 |
| 주제 적응 | 고정 화면·챕터 강제 금지 | 매번 주제 구조에 맞게 스토리·표현 선택, 고정 템플릿 복제 금지 |
| 최종 성공 기준 | 주제·핵심 관계 설명 여부 점검 | 원자료 없이 핵심 이해, 그 자리에서 세부·근거까지 접근 |

상세 기준은 [제작 스킬](../../plugins/byko-stack-codex/skills/byko-build-viewer/SKILL.md)에 두고, [뷰어 TOML](../../plugins/byko-stack-codex/agents/byko-viewer.toml)의 핵심 역할 지침과 [검토 스킬](../../plugins/byko-stack-codex/skills/byko-review-viewer/SKILL.md)도 같은 목적에 맞췄다. 기존 HTML 기본값, 접근성, 사실·예시 구분, 상호작용 상태 일치, 실제 브라우저 확인과 미검증 표시를 유지했다. 모델·effort, 에이전트 생성 방식과 스킬 자동 선택 정책은 변경하지 않았다.

검증: 제작·검토 스킬의 `quick_validate.py` 통과, 역할 준비 helper의 기존 테스트 6개 통과, 변경된 TOML·상대 참조·`git diff --check` 확인. 14개 원칙을 실제 문장과 대조했으며, 문구 일치만 검사하는 새 테스트는 추가하지 않았다. 이번 확인은 지침의 범위·일관성과 형식에 한정한다. 새 HTML 생성·브라우저 평가·설치본 업데이트는 수행하지 않았다.
