# byko-stack-codex 개선 계획

## 목적

스펙 기반 개발을 통해 사용자가 이루려는 실제 결과를 완성하고 검증하도록 돕는다. 현재 플러그인은 조사·설계·구현·검토라는 유효한 역할에 문서 동기화, 수치 게이트, 고정 수행 절차가 누적되어 매 작업의 부담을 키운다. 모델의 판단 역량을 활용하면서 목적과 문서·구현의 일관성은 더 명확히 유지한다.

### 요구사항

- 목적은 왜 필요한지, 무엇을 개발하고 어떤 요구사항을 충족해야 하는지, 어떤 실제 결과가 달성을 의미하는지를 포함한다. 요구사항을 목적과 별개의 기준으로 관리하지 않는다.
- 문서 판단, 방법 선택, 구현, 검증, 완료 모두 같은 목적을 따른다. 파일 생성·등록·테스트 통과 등 수단 수행을 목적 달성으로 대체하지 않는다.
- 목적과 방법 및 각각의 근거를 문서화한다. 필요한 조사와 중요한 질문은 하되, 질문 형식·가정 개수·사고 과정·작업 순서를 일률적으로 고정하지 않는다.
- 중단·재개와 인계에 필요한 상태와 검증 근거를 보존한다. 같은 결정과 진행 상태를 여러 표에 복제해 관리하지 않는다.
- 문서와 구현의 불일치는 디자인에서 재정립한다. 변경된 설계가 계획·코드·검증에 미치는 영향까지 반영하며, 구현을 정당화하기 위해 목적을 낮추지 않는다.
- 디자인과 개발이 독립 검토를 자동으로 수행하고 유효한 발견 사항을 수정·재검증한다. 사용자가 후속 검토 명령을 기억하거나 따로 요청할 필요가 없어야 한다.
- 검토는 구현이나 이전 결론에 맞춘 테스트를 피하고 목적에서 기대 결과와 반례를 도출한다. 실제 주변 영향과 검증 공백을 확인하며 범위와 비용은 변경에 비례한다.
- 설계만, 리뷰만, 구현까지라는 사용자 요청 범위를 보존한다. 자동 검토는 외부 쓰기나 미승인 제품 결정의 권한을 추가하지 않는다.

### 달성 확인

플러그인 파일 형식 검증만으로 위 목적을 달성했다고 판정하지 않는다. 격리된 임시 작업에서 실제 스킬을 사용해 다음 행동을 확인한다.

- 설계만 요청하면 목적 안에 요구사항과 결과 기준을 남기고, 방법과 근거를 설계하며 문서 검토까지 자동 수행한다. 구현으로 범위를 넓히지 않는다.
- 구현 요청은 직접 구현·검증·독립 리뷰·필요한 수정까지 이어진다. 문서와 코드가 어긋나면 설계를 정리하고 downstream 영향까지 반영한다.
- 리뷰는 잘못된 수단 중심 완료 기준이나 구현에 맞춘 테스트를 근거로 잘못 통과시키지 않는다. 확인한 문제와 검증하지 못한 범위를 구분한다.
- 재개는 기존 문서·현재 파일을 대조해 남은 일을 이어받고, 오래된 승인이나 테스트 결과를 새 변경의 검증으로 사용하지 않는다.

임시 fixture의 결과는 통제된 시나리오의 근거로 한정한다. 설치된 Codex의 자동 선택 빈도나 실제 프로젝트 전반의 성능 향상은 별도 실사용 확인이 필요하다.

## 방법

### 세 스킬과 자동 검토

- `codex-spec-designer`: 목적과 방법을 설계하고 문서 검토를 거쳐 설계를 완성한다.
- `codex-spec-dev`: 설계와 현재 코드를 바탕으로 목적 달성까지 구현·검증하고 구현 리뷰를 거친다.
- `codex-review`: 목적을 기준으로 문서와 구현을 독립 검토한다. 문서 모드와 구현 모드의 구체적인 검토 지침만 references로 나눈다.

검토 기준을 두 스킬에 중복 관리할 이유가 없어 `codex-eval-gate`는 `codex-review`에 통합한다. 사용되지 않았고 핵심 흐름에 필요하지 않은 `codex-claude-eval`은 제거한다. 기존 명령 전환은 README에 안내하고 기존 작업 산출물은 계속 읽을 수 있게 한다.

리뷰는 발견 사항을 반환하는 역할이다. 자동 호출한 디자인·개발이 수정과 필요한 재검토를 소유한다. 리뷰가 다시 개발을 호출하고 개발이 다시 리뷰를 호출하는 재귀 구조는 만들지 않는다. 사용자 결정이 필요하면 해당 결정과 영향만 명확히 묻고, 나머지 가능한 작업은 진행한다.

### 문서와 상태

새 작업은 기본적으로 `spec.md`와 `progress.md`를 쓴다. 설계에는 목적(요구사항·실제 결과 기준 포함)과 방법 및 근거를, 진행 문서에는 현재 상태·남은 일·변경 이유·검증/리뷰 근거와 재개 지점을 둔다. 상세 조사와 리뷰는 필요할 때만 별도 파일로 분리한다.

기존 프로젝트의 manifest와 산출물, CI가 참조하는 경로와 형식을 존중한다. 기존 파일을 일괄 이관하거나 새 문서 세트를 덧붙이지 않는다. 기존 goal/workflow 상태가 있으면 해당 상태 관리자를 통해 진행을 연결하며 중복 실행 관리 체계를 만들지 않는다.

### 유지할 제약과 맡길 판단

목적의 의미와 달성 기준, 사용자 권한 범위, 문서·구현 일관성, 독립 검토의 근거와 검증 한계는 명시한다. 조사 순서, 인터뷰 형식, 가정 수, 고정 agent 수, 정기 광역 테스트, 필수 요청서 복사·상태표 작성은 없앤다. 설계의 정확성을 위한 실제 의존 순서나 위험별 검증은 필요에 따라 남긴다.

`orchestrated-self-review`와 `adversarial-test-design`의 목적 우선·중립 컨텍스트·반례·실제 경계 검증 원칙을 가져오되 개인 설치 스킬을 필수 의존성으로 만들지 않는다. 플러그인만으로 사용할 수 있는 지침을 제공한다.

### 변경 범위

- `plugins/byko-stack-codex/`의 스킬, 공유 규약, 참조 자료, UI 메타데이터, plugin manifest
- 루트 한국어·영어 README의 해당 플러그인 설명
- 이 계획과 실행·검증 기록

Claude Code용 `byko-stack`, `byko-goal-codex`, 사용자 전역 스킬·설치 설정은 별도 요청 없이 변경하지 않는다. 이번 범위는 저장소 소스 개선이며 설치·배포·commit·push는 포함하지 않는다.

## 검증 기록

- 세 스킬의 `quick_validate.py`, `validate_plugin.py`, Markdown 상대 참조, UI metadata와 기본 implicit invocation, `git diff --check` 통과.
- 기본 Python에 PyYAML이 없어 첫 형식 검증은 실행 실패했다. 기존 uv cache의 PyYAML을 read-only로 연결해 재실행했으며 전역 설치·설정은 변경하지 않았다.
- 지침 본문·참조 문서는 1,660줄에서 260줄로 줄었다. 이는 구조 변화의 측정값이며 실제 개발 성능 향상의 증거는 아니다. 스킬 description 합계는 1,651자에서 237자로 줄었다.
- 독립 실행 fixture: `/private/tmp/byko-stack-forward-xij4849r/`. 각 실행자에게 원래 요청·대상 프로젝트·스킬 경로만 주고 예상 결론·의심 버그를 제공하지 않았다.

### 관찰한 문제와 수정

- 독립 정적 검토에서 이미 격리된 reviewer에게 재위임 의무가 적용될 수 있는 지침을 발견했다. 호출자의 독립 컨텍스트 구성과 reviewer의 직접 수행·반환을 분리했고 해당 finding의 해소를 재확인했다.
- 첫 설계 실행은 요구사항·달성 조건을 목적 밖의 절에 작성했다. 설계 본문에서 두 내용을 목적의 하위 내용으로 함께 작성하도록 명시했다. 세부 챕터·질문 수 등은 고정하지 않았다.
- 같은 실행에서 새 입력 방식의 설계 선택과 완료 상태 출처 확인을 모두 사용자 승인 대기로 남기는 경계를 관찰했다. 방법 미정 자체를 blocker로 삼지 않고, 목적과 허용된 범위 안의 선택은 근거로 결정하도록 질문 경계를 수정했다. 합의된 요구사항·보존 계약·권한 변경과 사용자만 알 수 있는 사실은 여전히 사용자 결정 경계다.
- 위 두 공유 지침 변경은 독립 정적 재검토에서 중요한 문제 없음으로 확인했다. 설계 시나리오는 새 컨텍스트에서 재실행했다. 디자이너가 다시 남긴 불필요한 승인 대기를 이번에는 자동 문서 reviewer가 원래 요청 기준으로 지적했다. 추가적인 세부 규칙을 더 쌓지 않고 기존 수정·재검토 흐름이 이를 처리하는지 확인했다.

### 실행 결과

| 시나리오 | 실제 관찰과 근거 |
|---|---|
| 중단된 구현 재개 | 기존 manifest를 상태 정본으로 유지했다. TXT 방법과 실제 JSON 계약의 충돌을 디자이너에서 수정하고 독립 문서 검토 후 개발했다. 구현 전 재등록 관련 테스트 4개 실패, 수정 후 7개 통과와 독립 구현 reviewer의 실제 파일 재현 3건을 확인했다. 반환 id·파일 bytes·mtime·기존 데이터와 문자열 구분을 검증했다. |
| 구현 리뷰 단독 요청 | 기존 테스트는 1개 통과했지만, 미리보기만 마스킹하고 실제 CSV에는 원문을 저장하는 오류를 독립 reviewer가 파일 재읽기로 재현했다. 코드·문서 변경 없이 수정 필요로 반환했고 git 작업 트리는 깨끗했다. |
| 첫 설계 전용 요청 | 코드 수정 없이 spec과 progress, 자동 독립 문서 검토를 수행했다. 설계 입력 계약을 사용자 결정으로 남기고 미검증으로 종료했다. 위 문서 구조·질문 경계 문제의 발견 근거로 사용했으며 성공 사례로 집계하지 않는다. |
| 설계 재실행 | 요구사항·실제 달성 조건이 목적 아래에 작성됐다. 원래 요청에 대한 독립 reviewer가 불필요한 승인 대기를 지적했고 디자이너가 수용했다. 별도로 테스트 사용자가 ‘호출자가 boolean 상태를 알고 있으며 전달 방식은 설계자가 선택한다’고 답한 뒤 수정 설계가 독립 재검토에서 통과했다. 코드 변경 없이 spec·progress 두 문서로 설계 요청을 완료했다. 원래 요청만으로 질문 없이 자동 수렴했다고 주장하지 않는다. |

임시 프로젝트의 단일 실행 결과이며 일반적인 실사용 성공률을 뜻하지 않는다. native goal lifecycle·실제 설치본의 스킬 자동 선택·운영 환경은 이 실행에서 검증하지 않았다. 새 지침에 목적상 의미 있는 영향을 받지 않은 구현·CSV 리뷰 시나리오는 불필요하게 반복하지 않았다.

최종 저장소 변경은 계획한 범위에 한정되며 `git diff --check`를 통과했다. plugin source 버전은 `0.3.0`이다. 설치·배포·commit·push는 수행하지 않았다. 실행 실험에서 요구한 독립 검토와 문서 보존은 확인했지만, 초기 판단이 항상 올바르거나 질문이 항상 최소라는 보장은 없으며 자동 검토·수정 흐름이 이를 보완한다.
