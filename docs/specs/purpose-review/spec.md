# 작업 준비와 단계별 검토 개선

## 목적

사용자가 작업을 건넸을 때 byko-stack-codex가 필요한 맥락을 조사·검토하고, 구현 방법에 끌려가지 않는 목표와 사전 검토 기준을 구체화하여 반복 설명·정정 부담을 줄인다. 한 번의 지시나 reviewer 판정으로 성공이 보장된다고 가정하지 않는다.

### 요청에서 확인된 계약

- 문제를 먼저 보고 조사 질문과 불확실성을 도출한다. 필요한 경우 그 질문에 적합한 관점·페르소나·범위·프롬프트를 구성해 위임한다. 고정 페르소나 목록·최소 인원·항상 같은 질문 양식은 요구하지 않는다.
- 목표를 누가·언제·어디서·무엇을·어떻게·왜의 관점으로 설명한다. '어떻게'는 결과가 성립해야 할 규칙이며 구현 구조를 미리 선택하는 칸이 아니다. 원래 요청·정정·확인된 사실과 에이전트 해석을 구분한다. 모르는 의도·정책은 지어내지 않는다.
- 분석 결과는 메인이 근거·누락·상충을 확인하고 필요하면 구체적인 사유와 재수행 범위를 반환한다. 새 근거 없는 반복은 중단 원인을 확인하고 필요한 질문이나 미검증으로 전환한다.
- 목표를 채택하기 전, 계획을 구현에 넘기기 전, 실제 결과를 완료로 판단하기 전에 단계에 맞는 검토를 수행한다. 작성 맥락에서 한 자체 확인을 독립 검토로 부르지 않는다. 이미 충분한 목표·검토 결과는 현재 변경과 대조해 재사용한다.
- 계획은 제품 정책·계약·보존 동작·중요한 실패 처리를 명확히 하되 구현자의 합리적인 내부 선택을 과도하게 고정하지 않는다. 정확성이 의존하는 상세 제약은 유지한다.
- 새 구현 전에 요청·목표·현행 코드에서 정상·반례·경계·보존 동작·영향받는 경로의 검토 가안을 만든다. 관련 축만 선택하고 관찰할 결과와 기대값의 근거를 남긴다. 후속 검토는 이 가안을 반드시 포함하면서 새 위험을 보완한다. 구현을 통과시키려고 기대값을 낮추지 않는다.
- 실제 결함이 없는 결과는 통과시킬 수 있어야 한다. reviewer 수·finding 수·테스트 개수·문서 생성만으로 품질을 판단하지 않는다.
- 현재 요청은 구현 허용이다. Claude Stack·Goal·전역 설정·설치 캐시·native agent 등록·새 하네스 구성·게시·commit/push는 범위 밖이다.

### 달성 조건과 사전 검증 기준

| ID | 관찰할 결과 | 실패로 보는 경우 |
|---|---|---|
| P1 | 목적만 요청하면 관련 근거를 조사하고 육하원칙의 구체적인 목표와 중요한 미확인을 반환 | 구현·계획까지 확대, 목적을 특정 함수/필드로 대체, 에이전트 제안을 고객 요구로 승격 |
| P2 | 위임을 결정할 때 문제와 독립 질문에 맞는 관점·범위를 선택 | 고정된 두 페르소나 또는 매 작업 전체 팀 구성, 원문 대신 메인 예상 결론만 전달 |
| P3 | 계획 리뷰가 현행 경로·제품 계약·구현 재량·검증 가안을 확인 | 정책 결정을 구현자에게 숨겨 넘기거나 내부 구조 취향만으로 반려 |
| P4 | 구현 전에 남긴 기대값·사례·근거가 후속 리뷰에서 추적되며 누락은 미검증으로 드러남 | 사례 삭제·기대값 완화로 통과, 구현 모양에서만 테스트 도출 |
| P5 | 유효한 결함과 정상 구현을 구분하고 올바른 단계로 수정을 반환 | 무조건 finding 생성, 같은 검증 반복, 증거 없는 통과 |
| P6 | 기존 상태·좁은 요청·권한 경계를 유지하고 위임 불가 시 가능한 일과 공백을 구분 | 문서 세트 강제, 전체 개발 루프 자동 확대, 독립성 허위 주장 |

기대 결과는 원래 요청과 보존 계약에서 얻는다. 현행 구현은 현재 동작과 변경 영향을 알아내는 자료이며 버그까지 정답으로 고정하지 않는다. 이번 개선의 행동 평가는 소수의 fixture에 한정하며 일반적인 사용자 개입 감소율을 입증하지 않는다.

## 방법

기존 9개 스킬·4개 역할·helper를 유지한다. 역할 TOML은 기본 책임, 전문 스킬은 수행 방법, workflow는 연결과 완료 판단을 담당한다. 새 runtime이나 강제 입력 schema를 만들지 않는다.

- `codex-spec-designer`: 요청/조사 → 목표와 검토 가안 → 목표 검토 → 방법·계획과 가안 보강 → 계획 검토. 목적만 요청하면 해당 결과까지만 반환한다. 기존 문서의 목적/방법 안에 기록하고 새로운 필수 파일을 추가하지 않는다.
- `byko-review-document`: 근거 공통 검토를 유지하고 목표·계획의 서로 다른 판단 기준을 필요한 때만 읽는 참조로 분리한다.
- `codex-review`와 `shared/delegation.md`: 단계·실제 쟁점에 맞는 질문과 위임을 구성한다. 최초 독립 평가에는 작성자의 예상 결론을 주지 않되 원래 요청, 사전 기준, 객관적인 위험 근거는 제공한다. 반려 후 특정 finding 재검증과 최초 독립 평가를 구분한다.
- `shared/verification.md`: 구현 전 기준 작성·근거·변경 이력·후속 리뷰에서의 처리·holdout 경계에 한정한 공통 계약. 고정 테스트 개수나 도메인별 목록을 넣지 않는다.
- 단독 구현/분석 스킬은 전체 workflow를 부르지 않으면서 필요한 사전 기준과 조사 범위를 확인한다. 코드 리뷰는 기준 대비 결과와 실제 사용 경계를 포함한다.
- 매니페스트를 0.5.0으로 올리고 한국어/영어 README와 기존 UI 설명을 맞춘다. 모델·effort·helper 인터페이스·자동 스킬 선택 정책은 유지한다.

## 검증 방법

변경 전 0.4.0을 임시 경로에 고정하고, 요청과 판정 기준을 먼저 만든 뒤 같은 입력을 새 컨텍스트의 동일 모델/effort 에이전트에 전달한다. 실행자에게 기대 판정·이전 결과·다른 버전의 지침은 주지 않는다. 이 공개 fixture는 구현자가 보았으므로 holdout이라고 부르지 않는다.

비교 사례는 목적만 정리하는 요청, 결함/정상 계획 검토, 사전 기준이 있는 구현 검토로 구성한다. 목표 검토·계획 검토·개발 연결은 추가 소규모 실행으로 확인한다. 각 사례의 원문·결과·수행 범위는 보고서에 남긴다. 실제 실행되지 않은 분기는 미검증이다. 문구·정규식 일치로 행동 통과를 판정하지 않는다.

형식 검사는 9개 스킬 validator, JSON/TOML/YAML 파싱, 패키지 상대 참조와 helper 6개 테스트를 사용한다. 독립 설계/최종 변경 검토에서 제기된 문제는 근거를 확인하고 관련 범위만 재검증한다.

## 설계 근거

- 현재 소스 기준: 시작 HEAD `8e3185f`; Codex Stack은 이전 `a643b7c`와 차이 없음. 기존 Claude Stack 후속 커밋과 미추적 PNG 자료를 보존한다.
- [OpenAI Build skills](https://learn.chatgpt.com/docs/build-skills?product=codex): 정확한 선택 범위와 필요한 지침의 점진적 로딩.
- [OpenAI 스킬·프롬프트 지침](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra): 결과/경계는 명확히, 중복·불필요한 절차는 축소. Astra 관찰을 현재 Sol의 검증 결과로 간주하지 않는다.
- [GPT-6 prompting](https://developers.openai.com/api/docs/guides/latest-model?model=gpt-6.1-sol): 실제 모델/작업에서 평가. 역할 기본값 `gpt-6.1-sol/high`를 고정해 지침 변경과 모델 변경을 섞지 않는다.
- [평가 지침](https://developers.openai.com/api/docs/guides/evaluation-best-practices): 사전 기준, 현실적인 요청, 반례, 변경 전후 비교와 평가 공백.
