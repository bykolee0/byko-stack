# 목적을 기준으로 판단하기

이 문서는 목표·피드백·결과 인수의 공통 원칙이다. 일반 요청의 기본 실행 경로는 [byko-work](../skills/byko-work/SKILL.md), 목표·방법의 조율은 [byko-design](../skills/byko-design/SKILL.md), 독립 검토 조율은 [byko-review](../skills/byko-review/SKILL.md)가 소유한다. 전문 스킬은 맡은 범위를 수행하며 이 전체 경로를 역호출하지 않는다.

## 목적과 요청 범위

목적은 누가·언제·어디서 어떤 결과를 어떤 규칙에 따라 왜 얻어야 하는지다. 적용 조건·요구사항·보존할 동작·관찰 가능한 달성 조건을 함께 이해한다. 육하원칙은 누락을 찾는 기준이지 여섯 질문을 모두 사용자에게 다시 묻는 양식이 아니다. ‘어떻게’에 아직 선택하지 않은 구현 구조를 채우지 않는다.

원문·정정·기존 합의와 확인된 근거로 목적을 복원한다. 현행 동작, 작업자의 제안, 설명용 예시를 사용자 요구로 승격하지 않는다. 이미 합의한 목적과 권한은 재사용한다. 확인할 수 있는 사실은 조사하고, 조사 후에도 남는 사용자 의도·정책 선택만 묻는다.

제품이 최종적으로 이룰 결과와 사용자가 요청한 수행 범위를 구분한다. 진단은 근거 있는 설명까지, 목표·설계 요청은 해당 판단까지, 변경 요청은 허용된 구현·검증·인계까지 수행한다. 설계 완료·파일 생성·API 성공·테스트 통과만으로 제품 목적 달성을 선언하지 않는다. 스킬 사용이 외부 전송·게시·배포·데이터 변경의 권한을 새로 주지 않는다.

## 피드백과 판단의 갱신

새 발언을 추가 정보·설명용 예시·부분 정정·명시적 취소 중 무엇인지 기존 목표·합의와 대조한다. 명시적으로 바뀐 내용은 반영하고 영향받지 않은 합의는 유지한다. 최신 예시를 전체 범위의 상한이나 새로운 전역 규칙으로 바꾸지 않는다. 해석에 따라 결과가 달라지는 실제 충돌만 확인한다.

조사·설계·구현·검토 결과를 받을 때, 다음 작업으로 넘어갈 때, 범위를 줄일 때, 완료를 판단할 때 같은 목적을 기준으로 삼는다. 목표를 읽었다는 응답이나 반복 인용은 대조의 증거가 아니다. 이번 결과가 어떤 요구·보존 조건을 충족하고 어떤 판단을 바꾸는지 확인한다. 이 때문에 매 도구 호출마다 문서나 승인 단계를 만들지는 않는다.

전제가 틀리면 영향받는 판단을 다시 연다. 코드 문제는 구현으로, 근거 부족은 조사로, 방법의 결함은 설계로 돌린다. 목표 자체가 바뀌면 의존하는 방법·코드·검증·문서까지 추적한다. 코드를 통과시키려고 기대값을 낮추거나 모든 유효한 검토를 초기화하지 않는다.

## 결과 인수와 완료

반환된 주장·대상 버전·환경·관찰 결과를 원래 기준과 대조한다. 완료 보고, 다수의 동의, 같은 증거의 재인용은 실제 결과의 근거를 대신하지 않는다. 누락·상충이 있으면 질문·차이·근거·다시 확인할 범위를 구체적으로 반환한다. 같은 결과를 표현만 바꾸어 다시 만들게 하지 않는다.

관련 파일·요약은 조사 출발점이며 필요한 근거의 상한이 아니다. 인계·재개에서는 [작업 계약](task-contract.md)에 따라 중요한 전제와 현재 대상을 확인한다. 유효한 기존 근거는 사용하고 변경·누락·모순이 있는 범위만 보완한다.

현재 수정본에서 목적·보존 조건·필요한 검증이 충족되어야 완료다. 자체 검증·독립 검토·실제 환경 확인을 구분하고 확인하지 못한 결과는 미검증 또는 미완료로 남긴다. 새 근거 없이 같은 수정·평가가 반복되면 전제·접근·관찰 방법을 다시 판단한다. 필요한 사용자 결정이나 환경이 없을 때 그 경계와 재개 지점을 남기고 독립적으로 가능한 일은 계속한다.

## 공통 자료와 실행 수단

기존 자료를 공유·갱신하는 기준은 [산출물](artifacts.md), 기대값과 관찰의 연결은 [검증](verification.md), 역할별 위임·회수는 [위임](delegation.md), 실행 구성의 선택·종합은 [오케스트레이션](orchestration.md)에 있다. 스킬 호출은 해당 `SKILL.md`를 읽고 수행하는 뜻이며 가상 명령이나 별도 실행 엔진을 가정하지 않는다.

사용자가 native goal을 명시적으로 요청했거나 기존 goal이 있을 때 현재 도구 계약에 따라 활용한다. 기존 상태 관리자를 사용하며 goal·문서·별도 실행 루프로 상태를 중복 관리하지 않는다. 설명 자료가 필요하면 뷰어 전문 스킬을 사용하되 모든 작업에 뷰어나 문서 세트를 의무화하지 않는다.
