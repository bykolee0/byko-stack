# 설계와 진행 상태

## 작업 찾기와 재개

사용자가 지정한 문서·경로와 현재 대화의 작업을 먼저 사용한다. 없으면 관련된 기존 설계와 상태 문서를 찾아 이어받는다. 서로 다른 작업이 실제로 구분되지 않을 때만 질문한다. 새 작업의 기본 위치는 `docs/specs/<작업명>/`이다.

기존 저장소의 문서 경로·형식과 CI 계약을 유지한다. `manifest.md`가 있으면 산출물 경로를 따라가고, ledger·plan·traceability·progress 중 현재 판단에 필요한 내용만 읽는다. 오래된 승인·진행 표시는 현재 파일과 대조한다. 불명확한 완료 상태를 그대로 이어받지 않는다.

진행 상태를 관리하는 문서는 하나를 정해 그 위치를 명시한다. 기존 manifest나 goal 상태 관리 체계가 있으면 그것을 사용한다. 기존 산출물을 일괄 삭제·이관하거나 과거 이력을 덮어쓰지 않는다. 이전 기록은 근거로 연결하고 새 현황을 여러 문서에 중복 기록하지 않는다. 저장소가 여러 파일의 갱신을 계약으로 요구하면 그 계약을 먼저 지킨다.

## 새 작업의 기본 문서

### `spec.md` — 목적과 방법

설계 본문은 목적과 방법을 중심으로 구성한다. 요구사항과 실제 달성 조건은 목적의 하위 내용으로 함께 작성한다. 목적 밖에 별도의 요구사항·완료 기준을 두어 판단 기준을 갈라놓지 않는다. 실제 결과의 기대값은 목적에, 그 결과를 만들고 확인하는 접근은 방법에 둔다. 그 안의 상세 구성과 분량은 작업에 맞춘다.

- **목적**
  - 문제와 배경: 왜 필요한지, 누구·어떤 호출자가 어떤 결과를 얻어야 하는지
  - 요구사항과 범위: 개발할 동작, 지킬 계약과 보존할 기존 동작
  - 달성 조건: 실제로 무엇이 되어야 하는지와 이를 확인할 근거. 구현·문서·등록·테스트 수행 사실이 그 결과를 대신하지 않게 쓴다.
- **방법**
  - 현재 구조·관련 근거와 선택한 해결 방식, 그 방식이 목적에 적합한 이유
  - 구현과 통합에 필요한 계약·영향·검증 접근, 정확성에 필요한 의존 순서
  - 중요한 결정과 선택 이유, 남아 있는 불확실성과 그 영향

작은 변경은 짧은 문서로 충분하다. 범위가 커지면 읽고 변경하는 단위에 맞춰 분리하고 상위 문서에서 연결한다. 고정 챕터나 완전한 코드 수준 설계를 요구하지 않는다. 다만 필요한 결정을 모호한 표현으로 숨기지 않는다.

### `progress.md` — 재개에 필요한 현재 상태와 근거

새 작업에 기존 상태 관리자가 없을 때 사용한다. 다음 사람이 전체 대화를 복원하지 않고 이어갈 수 있게 기록한다.

- 설계 문서 경로, 현재 요청 범위와 작업 단계
- 완료한 결과, 진행 중인 일, 남은 일과 다음 행동
- 변경 이유와 아직 필요한 결정·환경
- 실제로 수행한 검증·리뷰의 대상과 결과, 미검증 범위
- 재개 시 다시 확인해야 할 변경·리뷰 사항

작업 분해나 AC ID는 추적이 유용할 때 사용한다. 별도 plan·traceability·ledger를 의무로 생성하지 않는다. 의미 있는 결과·결정·중단 시 상태를 갱신하되 모든 도구 호출을 기록하지 않는다.

## 검토와 설계 변경 기록

리뷰 결과에는 검토한 문서·코드 범위와 그 버전을 식별할 근거(커밋과 working diff, 관련 파일의 hash 등)를 남긴다. 시간만으로 변경 전후를 구별하지 않는다. 설계 검토 통과와 구현 검증 완료를 구분한다.

발견 사항과 해결 근거는 진행 문서에 남긴다. 길면 `review-results/` 등 기존 위치에 분리하고 진행 문서에서 연결한다. 문서 원문을 요청서에 다시 복사할 필요는 없다.

설계 수정 시 목적·방법 중 무엇이 바뀌었는지, 이유와 영향받는 산출물·검증을 기록한다. 수정 전 결과를 새 버전의 통과 근거로 쓰지 않는다. 무관한 검증까지 초기화하지는 않는다.

독립 리뷰만 요청받은 경우에는 응답으로 결과를 제공한다. 저장소에 보고서를 쓰거나 상태를 갱신하는 것은 사용자가 요청했거나 디자인·개발 workflow의 일부로 호출된 경우에 한다.
