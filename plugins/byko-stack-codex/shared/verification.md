# 구현 전 기준과 후속 검토

새 구현을 보기 전에 원래 요청·목표·유효한 계약과 현행 코드를 바탕으로 검토 가안을 만든다. 현행 코드는 현재 사실과 영향을 알아내는 자료이며 기존 버그까지 기대값으로 삼지 않는다. 목표를 구체화하면서 가안을 시작하고, 계획에서 필요한 검증 경로를 보완한다. 기존 기준이 충분하면 재사용한다.

## 가안에 남길 판단

목표를 만족하는 정상 동작, 적용하면 안 되는 반례, 경계·실패, 보존해야 할 동작과 영향받는 연결 중 관련된 축을 선택한다. 특정 도메인의 체크리스트나 최소 사례 수를 모든 작업에 적용하지 않는다.

각 중요한 확인에는 조건·기대하는 관찰 가능 결과·기대값의 출처·확인 방법을 남긴다. 반환값만으로 충분하지 않으면 저장 상태·전송·후속 효과 등 실제 결과가 드러나는 경계를 포함한다. 기대값을 결정할 근거가 없으면 필요한 정책 결정이나 탐색 항목으로 남기고 통과/실패로 집계하지 않는다.

기존 문서의 목적·검증 접근 또는 기존 테스트에 기록한다. 추적이 필요하면 짧은 ID를 쓰되 별도 파일·고정 표 양식을 강제하지 않는다. 기준을 만든 시점의 요청·코드 버전을 구별할 근거를 남겨 이후 구현에 맞춰 소급 작성한 기준과 구분한다.

## 후속 검토에서의 사용

사전 기준은 후속 리뷰의 필수 입력이다. 중요한 항목마다 결과와 근거, 미확인 여부를 추적할 수 있게 한다. 현재 버전에서 이미 충분히 확인한 근거는 활용하고 같은 검사를 무조건 다시 실행하지 않는다. 검증 불가를 항목 삭제나 통과로 바꾸지 않는다.

계획·구현에서 새로 드러난 위험을 추가한다. 사전 목록 통과만으로 전체 목적 달성을 선언하지 않는다. 기준이 틀렸거나 요구가 바뀌었다면 원래 근거와 대조해 변경 이유·영향·대체 기준을 남긴다. 구현을 통과시키기 위해 기대값을 완화하지 않는다. 무관한 기준까지 초기화하지 않는다.

구현 후에 기준이 없다는 사실을 발견해도 리뷰를 포기하지 않는다. 원래 요청과 변경 전 자료로 기대 결과를 재구성하되 사전 작성이라고 주장하지 않는다. 확인 가능한 결과와 남은 공백을 구별한다.

공개된 기준은 구현자와 공유해도 된다. 구현자에게 실제로 격리한 추가 사례만 holdout이라고 부른다. 같은 저장소를 공유하는 새 agent라는 이유만으로 파일 접근까지 격리됐다고 보지 않는다. 구현 후 새로 만든 반례는 후속 반증으로 구분한다.
