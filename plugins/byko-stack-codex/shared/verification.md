# 변경 전 기준과 실제 결과의 검증

새 구현을 보기 전에 원래 요청·목표·유효한 계약과 현행 근거로 기준을 만든다. 현행은 현재 사실과 영향을 알아내는 자료이며 기존 버그까지 기대값으로 삼지 않는다. 목표를 구체화하면서 기준을 시작하고 계획에서 관찰 방법을 보완한다. 기존 기준이 충분하면 재사용한다.

## 기대값과 보존 조건

현재 무엇이 발생하는지(as-is), 어떤 조건에서 무엇이 달라져야 하는지(to-be), 무엇이 그대로여야 하는지를 구분한다. 정상 동작·적용하면 안 되는 반례·경계·실패·보존·영향받는 연결 중 관련된 축을 선택한다. 고정 사례 수나 특정 업무 체크리스트를 모든 작업에 적용하지 않는다.

각 중요한 확인에는 조건·관찰 가능한 기대 결과·기대값의 출처·확인 방법을 남긴다. 반환값만으로 부족하면 저장 상태·전송·후속 효과·사용자 화면 등 실제 결과가 드러나는 경계를 포함한다. 실제 데이터 상태와 데이터 흐름은 별도 근거가 필요할 수 있다. 기대값을 결정할 근거가 없으면 필요한 정책 결정이나 조사 질문으로 남기고 임의의 통과/실패를 만들지 않는다.

기존 문서·테스트·짧은 작업 기록에 연결하며 별도 파일·고정 표 양식을 강제하지 않는다. 기준을 만든 시점의 요청·대상 버전을 구별할 근거를 남겨 구현에 맞춰 소급 작성한 기준과 구분한다. 단독 전문 작업에서는 맡은 결과의 확인에 필요한 수준만 준비한다.

## 기존 검증 경로를 실제로 사용하기

기존 리포의 테스트·실행 방법·검증 harness를 먼저 확인한다. 사용자 또는 호출자의 실제 접점에서 시작·조작·관찰할 수 있는지, 필요한 버전·프로세스·설정·인증·데이터와 실행 권한이 맞는지 확인한다. 기존 경로가 충분하면 재사용하며 검증을 위해 새 시스템을 자동 도입하지 않는다.

중요한 결과를 관찰할 방법이 부족하면 그 공백만 보완하고 **보완한 방법 자체를 실제로 실행**한다. 스크립트·테스트·검증 문서를 만들었다는 사실을 성공으로 세지 않는다. 테스트 전용 setter나 내부 성공 표시가 실제 사용 경계를 대신하지 않는지 확인한다. 임시 데이터·프로세스의 소유권과 정리 방법을 정하고 정리 후에도 판단에 필요한 실행 근거는 남긴다.

재현은 가설을 구별하는 강한 방법이지만 재현 실패가 결함 부재를 뜻하지 않는다. 운영 흔적·코드 경로·대조 관찰로 확인한 범위와 환경 차이를 구분한다. 접근 불가를 미관찰과 구별하며 허용 범위를 넘어 실행하지 않는다. 문서 drift, 검증 방법의 공백, 제품 회귀를 구분하고 테스트 기대값을 바꿔 제품 문제를 숨기지 않는다.

## 실행 증거와 후속 검토

사전 기준은 후속 리뷰의 입력이다. 중요한 항목마다 실제 명령·대상 수정본·환경·관찰 결과와 미확인을 연결한다. 계획한 검사와 실제 수행한 검사, 자체 점검과 독립 검토, 로컬과 통합·대상 환경 확인을 구분한다. PR 생성·CI 통과·배포 성공은 실제 동작 확인을 대신하지 않는다.

현재 버전에서 충분히 확인한 근거는 활용하고 같은 광역 검사를 무조건 반복하지 않는다. 새 변경·실패·미해결 위험에 해당하는 범위만 추가 확인한다. 구현·계획에서 새로 드러난 위험을 보완하며 목록 통과만으로 목적 달성을 선언하지 않는다.

기준이 틀렸거나 요구가 바뀌면 원래 근거와 대조해 이유·영향·대체 기준을 남긴다. 구현을 통과시키려고 기대값을 낮추지 않는다. 검증 불가를 항목 삭제나 통과로 바꾸지 않으며 무관한 기준까지 초기화하지 않는다. 구현 후 기준 부재를 발견하면 원래 요청·변경 전 자료로 재구성하되 사전 작성이라고 주장하지 않는다.

공개된 기준은 구현자와 공유할 수 있다. 실제로 격리한 추가 사례만 holdout이라고 부른다. 같은 저장소를 공유하는 새 agent는 파일 접근까지 격리된 것이 아니다. 구현 후 만든 반례는 후속 반증으로 구분한다.
