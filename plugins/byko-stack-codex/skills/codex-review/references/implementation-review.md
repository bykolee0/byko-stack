# 구현 리뷰

원래 목적을 충족하면서 변경이 기존 시스템에 안전하고 단순하게 통합됐는지 확인한다. 문서·코드·테스트가 서로 같은 주장을 한다는 것만으로 정확하다고 판단하지 않는다.

## 목적에서 기대 결과 도출

구현과 기존 테스트를 기준으로 삼기 전에 원래 요청·목적 문서·보존 계약에서 기대 결과와 중요한 반례를 도출한다. 확인할 대상에는 기능의 결과뿐 아니라 목적상 중요한 부수 효과도 포함한다. 목적이 모호하면 현재 코드로 정답을 정의하지 않는다.

현재 설계가 원래 목적을 좁혔는지도 검토한다. 설계와 구현이 다르면 어느 쪽이 목적과 근거에 맞는지 설명하고, 설계 재정립 또는 코드 수정이 필요한 지점을 반환한다.

## 실제 경계와 주변 영향

현재 repo·변경 범위·base를 확인하고 관련 컨벤션과 실제 호출 흐름을 따른다. 변경이 닿는 계약·데이터·권한·비동기 작업·배포 경계 중 관련된 부분을 선택해 조사한다. 변경 파일에 나타난 타입이나 mock 사이에서 멈추지 말고 실제 저장·전송 형태와 downstream 동작을 확인한다.

기존 동작의 회귀, 오류와 부분 실패, 상태 변화·중복·순서, 혼합 버전과 롤백 등 목적 달성이 의존하는 위험을 확인한다. 코드의 응집도·책임·의존 방향·중복과 불필요한 추상화도 실제 유지보수 영향으로 판단한다. 특정 backend·언어·운영 환경을 모든 프로젝트의 전제로 삼지 않는다.

## 적대적 검증

설계·구현이 참이라고 가정하는 조건을 깨는 반례를 만든다. 변경에 관련된 정상·보존·경계·실패·호환성 행동을 선택하고 입력·사전 상태·기대 결과와 근거를 정한 다음 실행 결과와 대조한다. 케이스 수를 채우거나 구현의 분기를 그대로 테스트 목록으로 옮기지 않는다.

mock이 숨길 수 있는 실제 연결 경계에서 가장 작은 유효한 재현을 실행한다. 목적상 필요하면 반환값 외에 저장 상태, 선택된 식별자, 이벤트·payload, 실패 후 부수 효과를 관찰한다. 관련 실패는 base에서도 발생하는지 확인해 변경으로 생긴 문제와 구분한다.

구현자에게 공개되지 않은 케이스만 holdout으로 부른다. 이미 알려진 사례나 구현 후 추가한 반례는 그 출처를 정확히 밝힌다. 현재 구현을 통과시키기 위해 기대값을 바꾸지 않는다.

## 충분성과 종료

저장소가 요구하는 검사와 중요한 위험을 확인하는 테스트·실행 검증을 수행한다. 전체 suite와 추가 탐색은 새 근거가 필요한 경우에 선택한다. 다른 reviewer가 이미 실행한 광역 테스트를 중복 실행하지 않는다.

핵심 결과를 판단할 실행 근거가 없으면 그 부분을 미검증으로 남긴다. 환경이 없거나 비용·권한 때문에 필요한 검증을 못했다면 구현 통과나 merge 준비 완료로 확대하지 않는다. 단, 목적에 적합한 정적 근거로 확인 가능한 변경에 무관한 실행 환경을 요구하지 않는다.

수정 후에는 해당 반례와 영향을 받은 보존 동작을 재확인한다. 테스트 통과 개수보다 어떤 목적·위험을 확인했는지, 무엇이 남았는지로 판정한다.
