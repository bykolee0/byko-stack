# 목표와 방법의 설계

[공통 원칙](../../shared/workflow.md)을 읽는다. 원래 요청·정정·현행 근거로 구현과 검증에 사용할 기준을 만든다. 전체 작업 조율은 호출자가 소유하며 이 스킬이 개발 전체를 다시 호출하지 않는다.

## 조사와 목표

원문과 기존 분석·현재 코드·관련 계약을 대조한다. 인계 요약에 없는 연결도 맡은 결정에 영향을 주는지 확인한다. 부족한 근거는 [byko-analyze](../byko-analyze/SKILL.md)를 읽고 직접 보완하거나 [분리 조사](../../shared/orchestration.md#분리-조사와-종합)로 맡긴다. 사용자만 정할 정책과 조사로 알 수 있는 사실을 구별한다.

[산출물 관리](../../shared/artifacts.md)의 육하원칙으로 원하는 결과·적용 조건·이유·범위를 식별한다. 원문 요구, 확인한 사실, 선택한 해석과 미확인을 구분한다. 목표를 방법이나 문서 작성으로 대신하지 않는다.

[사전 검증 기준](../../shared/verification.md)을 읽고 바꿀 동작과 보존할 계약, 기대값 출처와 관찰 방법을 준비한다. 현행 버그까지 보존 대상으로 삼지 않는다. 목표를 계획의 기준으로 채택하기 전에 [byko-review](../byko-review/SKILL.md)의 목표 검토를 수행한다. 이미 유효한 검토는 재사용한다. 목표만 요청받았으면 목표·근거·검토 결과·남은 판단을 반환한다.

## 방법과 계획

목표·보존·사전 기준을 [byko-propose](../byko-propose/SKILL.md)에 전달하고 해당 스킬을 읽어 방법을 작성한다. 조사로 충분히 한정된 선택은 직접 수행할 수 있다. 중요한 대안이나 실패 영향이 있으면 [후보 비교](../../shared/orchestration.md#후보-작성과-비교)를 읽고 독립 후보와 검토를 구성한다. 의미 없는 대안을 수 채우기용으로 만들지 않으며 하나의 방법만 남는다면 제약과 확인 근거를 설명한다.

정확성에 필요한 정책·공개 계약·실패 처리·순서와 검증 경로를 명확히 하고 같은 계약을 충족하는 내부 구현 선택은 맡긴다. 후보의 전제·장단점·반례를 근거로 비교하며 모든 후보가 탈락할 수 있다. 선택한 방법과 이유, 영향받는 대상, 미결정을 기존 자료에 갱신한다.

구현에 넘기기 전에 `byko-review`를 읽고 계획 검토를 수행한다. 목표와 계획이 이미 함께 준비되어 있다면 한 독립 검토에서 두 판단을 구별할 수 있다. 목표 오류는 목표로, 근거 공백은 조사로, 방법 결함은 후보 보완으로 돌리고 영향받는 기준만 재검토한다.

## 변경과 반환

개발 중 전제가 틀리거나 코드와 계획이 어긋나면 원래 목표·근거로 어느 쪽을 바꿀지 판단한다. 설계가 맞으면 구현 수정을 반환하고, 설계 변경이 필요하면 관련 기준·문서·검토를 먼저 갱신한다. 구현에 맞춰 기대값을 낮추지 않는다.

현재 목표와 선택안, 보존·검증 기준, 검토 대상·결과, 미결정·미검증을 호출자에게 반환한다. 독립 검토를 못 했으면 그 공백을 명시한다. 설계 완료를 제품 목적 달성으로 보고하지 않는다. 설명 뷰가 목적에 포함되면 뷰어 전문 스킬을 연결하되 설계 문서의 자동 변환이나 별도 문서세트를 요구하지 않는다.
