# 목표와 방법의 설계

[공통 원칙](../../shared/workflow.md)을 따른다. 요청과 근거로 목표를 정립하고, 목표를 달성할 계획을 검토된 구현 기준으로 만든다. 목표만 요청하면 목표까지, 설계만 요청하면 계획까지 수행한다.

## 요청에서 조사 질문 찾기

원래 요청·정정과 기존 목적·코드·계약을 확인한다. 지금 무엇을 알아야 다음 판단을 할 수 있는지 정하고, 조사로 알 수 있는 사실과 사용자만 정할 의도·정책을 구분한다. 이미 충분한 내용을 재질문하지 않는다.

[위임 지침](../../shared/delegation.md)에 따라 질문에 적합한 관점과 범위로 `byko-analyst`를 구성하거나 짧은 확인에 [byko-analyze](../byko-analyze/SKILL.md)를 직접 적용한다. 결과의 근거·누락·상충을 확인하고 필요한 부분만 사유를 밝혀 재조사한다. 분석가의 초기 해석을 확정 목적이나 설계 승인으로 취급하지 않는다.

## 목표와 목표 검토

[문서 관리](../../shared/artifacts.md)의 육하원칙으로 원하는 결과를 구체화한다. 적용 조건·범위·동작·이유를 유지하며 추상적인 미사여구나 구현 구조로 목적을 대신하지 않는다. 원래 요청에서 확인되는 요구와 선택한 해석·미확인을 구분한다.

[사전 검토 가안](../../shared/verification.md)을 시작한다. 어떤 결과가 나오면 목적을 달성했다고 볼지 생각하면서 중요한 모호함을 드러낸다. 목표에 의존하는 계획을 확정하기 전에 [codex-review](../codex-review/SKILL.md)의 목표 검토를 수행한다. 근거가 부족하면 조사로, 목적 해석이 틀리면 목표 수정으로 돌아간다. 사용자만 정할 사항에 의존하지 않는 작업은 계속한다.

기존 목표와 검토 근거가 현재 요청에도 충분하면 재사용한다. 목표 정립만 요청받았다면 목표·근거·검토 결과·중요한 미확인을 반환하고 마친다. 별도 파일이나 구현 계획을 자동으로 추가하지 않는다.

## 계획과 계획 검토

목표를 달성할 방법과 선택 이유를 실제 코드베이스·관련 계약에 맞게 정한다. 제품 동작·정책·호환성·중요한 실패 처리는 구현자가 임의로 결정하지 않아도 되게 명확히 한다. 같은 계약을 충족하는 내부 구현 선택은 맡기며, 정확성이 의존하는 제약과 순서는 구체적으로 남긴다.

목표 단계의 검토 가안을 현행 경로와 변경 영향에 맞춰 보강한다. 구현 전에 기대 결과·근거·관찰 방법을 남기고, 모르는 기대값을 채워 넣지 않는다. 기존 문서의 목적·방법·진행 상태에 연결하며 새 문서 세트를 요구하지 않는다.

계획을 구현에 넘기기 전에 `codex-review`의 계획 검토를 수행한다. 유효한 발견 사항을 반영하고 영향받은 판단만 재검토한다. 목표를 다시 바꾸었다면 관련 목표 검토도 갱신한다. 사용자가 검토를 따로 호출하거나 통상적인 수정을 매번 승인하게 하지 않는다.

## 변경·반환

개발 중 전제가 틀리거나 설계·코드가 어긋나면 원래 목적과 근거로 원인을 판단한다. 설계가 옳으면 구현 수정을 반환하고, 설계 변경이 필요하면 관련 문서·검토·사전 기준을 먼저 맞춘다. 코드를 통과시키려고 목표를 낮추지 않는다.

설명 자료가 필요하면 `byko-viewer` 또는 [byko-build-viewer](../byko-build-viewer/SKILL.md)를 적용하고 검토에 내용·이해·탐색을 포함한다. 형식 미지정 시 HTML이며 기존 문서의 자동 변환을 요구하지 않는다.

현재 요청에서 준비된 결과와 근거, 미결정·미검증, 다음 작업에 미치는 영향을 반환한다. 독립 검토를 못 했으면 그 공백을 밝힌다. 설계 완료를 제품 목적 달성으로 보고하지 않는다. 개발 요청 중 호출됐다면 확인된 기준과 영향 범위를 개발에 반환해 이어간다.
