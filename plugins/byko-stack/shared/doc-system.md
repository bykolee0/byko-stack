# 사람용 문서 규약

byko-stack이 만드는 산출물 중 **사람이 읽고 판단하는 것**은 HTML로, **에이전트가 읽고 갱신하는 것**은 마크다운으로 만든다. 형식은 취향이 아니라 독자가 정한다.

## 무엇을 HTML로 만드나

| 산출물 | 주 독자 | 형식 |
|--------|---------|------|
| `index.html` | 사람 — 진입점 | HTML (manifest.md에서 **생성**) |
| `spec.html` | 사람이 승인, 에이전트가 구현 | HTML (**저작**) |
| `implementation-plan.html` | 사람이 착수 승인 | HTML (**저작**) |
| `manifest.md` · `ambiguity-ledger.md` · `traceability.md` · `progress.md` · `analysis/` · `eval-results/` · `review-results/` | 에이전트 | md |

새 산출물이 생기면 같은 기준으로 판단한다: **사람이 이걸 열어서 결정을 내리는가?**

## 이 문서들은 명세서가 아니라 해설이다

가장 중요한 규칙이다. 스펙은 "무엇을 만들지 나열한 문서"가 아니라 **"이 변경을 이해시키는 글"**이다. 카드와 표를 잔뜩 늘어놓은 명세서는 읽는 사람에게 아무것도 남기지 못한다.

세 가지가 성립해야 한다.

1. **탑다운** — 큰 그림을 먼저 주고 점점 좁혀 들어간다. 결론은 0장에 있다.
2. **배경이 먼저** — 이해에 필요한 개념·현재 구조·정상 흐름을 깔고 나서 변경을 말한다. 배경 없이 결과부터 주면 사람은 따라오지 못한다.
3. **스토리** — 개념을 나열해 주면 머릿속에서 저절로 연결되지 않는다. `지금 이렇다 → 그래서 막힌다 → 이렇게 바꾼다 → 그러면 이렇게 된다`로 잇는다.

**규칙을 읽기 전에 실물을 먼저 보라: `examples/spec-example.html`.** 이 문서 하나가 아래 설명보다 빠르다.

## 문서 골격

`byko-doc new`가 만들어 준다. 표지 한 장 + 번호가 붙은 챕터들.

**spec** — `0.한 문장 · 1.개념 · 2.현재 구조 · 3.정상 흐름 · 4.막히는 지점 · 5.바꾸는 것 · 6.결정할 것 · 7.완성 조건 · 8.만드는 순서 · 9.기억할 것`

**plan** — `0.한 문장 · 1.왜 이 순서 · 2.단계 · 3.영향 범위 · 4.승인할 것 · 5.AC 매핑`

챕터를 더하거나 빼도 되지만 **1~4장(개념 → 현재 → 정상 → 문제)을 건너뛰고 5장부터 시작하지 않는다.** 그 순서가 이 문서의 존재 이유다.

**표지에 반드시 넣을 것**: 무엇을 왜 읽는지 한 문단(`hero-sub`), 그리고 **끝까지 기억할 단어 2~3개**(`.remember`). 독자가 붙잡을 손잡이가 있어야 나머지가 읽힌다.

## 제목은 라벨이 아니라 장면이다

| 이렇게 쓰지 않는다 | 이렇게 쓴다 |
|---|---|
| 도메인 규칙과 데이터 | 주문 하나에는 사실 세 개의 층이 있다 |
| 문제점 | "3개 중 1개만요"라는 한 마디가 길을 끊는다 |
| 아키텍처 변경 | 취소를 '상태'가 아니라 '사건'으로 바꾼다 |
| 동시성 처리 | 두 사람이 동시에 누르면 무슨 일이 벌어지나 |
| Acceptance Criteria | 무엇이 되면 다 만든 것인가 |

두 줄로 끊고 뒷줄을 `<span class="accent">`로 강조하면 표지 제목이 살아난다.

## 개념은 실물에 빗대어 세운다

내부 코드 이름부터 던지지 않는다. **무엇에 해당하는지**를 먼저 말하고 코드 이름은 뒤에 붙인다.

> 주문 = **영수증 한 장** · 주문 아이템 = **영수증의 한 줄** · 취소 단위 = **한 줄에서 몇 개를 무르는 사건**

비유가 정확하지 않으면 쓰지 않는다. 어설픈 비유는 오해를 만든다.

## 시각화는 도메인을 본뜬다

**박스-화살표 SVG 다이어그램을 그리지 않는다.** 정보량이 거의 없고, 만드는 데 드는 노력에 비해 이해를 돕지 못한다. 대신 설명하려는 대상의 구조를 그대로 본뜬 HTML 컴포넌트를 쓴다.

| 무엇을 보여주나 | 무엇을 쓰나 |
|---|---|
| 한 건이 어떻게 처리되는가 | `.story` — 번호 붙은 단계. 문제는 `.problem`, 해법은 `.fix` |
| 지금 구조가 어떻게 생겼나 | `.map` + `.map-box` + `.plane-tag` + `.code-ref` |
| 개념 정의 | `.terms` + `.big-word` + `.like` |
| 무엇이 어떻게 달라지나 | `.beforeafter` (from → to) |
| 완성 조건 | `.scenario` — 상황 버튼을 눌러 결과를 본다 |
| 만드는 순서·되돌릴 수 있는 경계 | `.pipeline` |

마크업은 `doc-snippets.md`에 있다. 정말로 좌표가 필요한 그림(상태 전이 등)만 예외적으로 인라인 SVG를 쓰되, CDN·mermaid는 쓰지 않는다.

## 사람이 결정할 것은 표시한다

판단이 필요한 지점만 표시한다. 표시한 것들은 `byko-doc build`가 **결정 목록**으로 모아 6장 상단에 넣는다.

| 값 | 무엇을 표시하나 |
|----|----------------|
| `new` | 이 프로젝트에서 처음 생기는 도메인 개념·용어 |
| `type` | 새 타입·스키마·인터페이스·모듈 경계 |
| `data` | 마이그레이션·백필·저장 포맷 변경 |
| `decision` | 유저 확인 없이 정한 것 (ledger의 `assumed`) |
| `risk` | 되돌리기 어려운 것 — 공개 API, 보안, 비용, 외부 계약 |
| `open` | `[TBD]`·blocking — 사람만 답할 수 있는 것 |

```html
<div class="rv" data-rv="type" data-rv-title="목록에서 읽힐 한 문장">
  <div class="rv-head">
    <span class="chip" data-rv="type" data-icon="▣">새 구조</span>
    <span class="rv-title">…</span>
    <span class="rv-why">왜 사람이 봐야 하나</span>
  </div>
  <p>무엇을 정했는지 · 왜 그렇게 정했는지 · <strong>검토했던 대안</strong>과 기각 이유</p>
</div>
```

- `data-rv-title`이 결정 목록에 뜨는 문장이다. **목록만 훑어도 무엇을 봐야 하는지 알게** 쓴다.
- **악센트는 아껴 쓴다.** 전부 강조하면 아무것도 강조되지 않는다. 스펙 하나에 5~8건이면 많은 편이다.
- 결정 목록(`byko:review-queue` 영역)은 스크립트가 만든다. 직접 쓰지 않는다.

## 기계적 변경은 접어 둔다

리네임·파일 이동·반복 치환·픽스처 갱신은 사람의 시선을 뺏지 않게 접는다. 구현 에이전트는 펼쳐서 읽는다.

```html
<details class="agent-only"><summary>기계적 변경 목록</summary><ul><li>…</li></ul></details>
```

## 도구

```bash
# 스크립트 경로는 세션에서 한 번만 확인한다 (설치 위치가 환경마다 다르다)
BD="${CLAUDE_PLUGIN_ROOT:-}/scripts/byko-doc.py"
[ -f "$BD" ] || BD=$(find ~/.claude/plugins -path '*byko-stack*' -name byko-doc.py 2>/dev/null | head -1)

python3 "$BD" new --kind spec --title "<장면형 제목>" --project <name> \
                  --out docs/specs/<name>/spec.html
python3 "$BD" build docs/specs/<name>   # 챕터 목차·결정 목록 생성 + manifest.md → index.html
python3 "$BD" check docs/specs/<name>   # 구조 검증 (오류 0이어야 한다)
python3 "$BD" text  docs/specs/<name>/spec.html   # 평문 추출 (codex에 본문을 넘길 때)
python3 "$BD" pack  docs/specs/<name>/spec.html   # css/js 인라인한 단일 파일 (외부 공유용)
```

**문서를 고칠 때마다 `build` → `check`.** `check`는 표지·챕터 수·완성 조건·태그 구조를 본다. 오류가 나면 유저에게 보여주기 전에 고친다.

## 기존 문서를 고칠 때

- 생성 영역(`<!-- byko:chapnav:… -->`, `<!-- byko:review-queue:… -->`) 안은 건드리지 않는다. 다음 `build`가 덮어쓴다
- 새 챕터에는 `id`와 `data-nav`(짧은 라벨)를 붙인다
- 결정이 바뀌면 악센트도 갱신한다 — 해소된 `open`은 내리고, 새로 생긴 판단거리는 표시한다. **결정 목록은 "지금 사람이 볼 것"이어야 의미가 있다**
- 고친 뒤 `build` → `check`
