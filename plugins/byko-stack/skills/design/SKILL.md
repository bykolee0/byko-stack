# design

> 재진입: `.byko/work/<작업>/record.md` → `brief.md` 순으로 읽는다. 기록이 있는데 work의 규칙이 지금 보이지 않으면(압축 뒤) `/byko-stack:work`를 다시 불러 잇는다. 기록 없이 단독으로 불렸으면 work를 부르지 않는다.

변경 경로의 D1(방법), D2(검증 기준), D3(설계 검증)를 닫는다. 결과는 `brief.md` 검증 기준 절, `design.md`, `record.md` D 항목에 남는다. 세 파일은 메인만 쓴다.

**단독 호출.** 기록이 없으면 `${CLAUDE_PROJECT_DIR}/.byko/work/<yymmdd-이름>/`에 필요한 만큼의 `brief.md`(첫 줄 `# 무엇을 왜`, 요청 원문 위치·대목표·범위·기준)와 `record.md`(첫 줄 `> 재진입: 이 파일 → brief.md 순으로 읽는다`, 둘째 줄 `지금: 경로 · 다음 · 상태`, 이어서 열린 항목)를 만든다. 처음이면 `.byko/.gitignore`에 `*` 한 줄을 둔다. as-is가 조사되지 않았으면 먼저 조사한다. 설계·계획만 요청받았으면 구현하지 않는다. 구현 뒤에 세운 기준은 '사후 재구성'으로 표시한다. 위임 결과가 모두 돌아오기 전에는 비교·종합하지 않는다. `-p`에서는 결과까지 기다린 뒤 턴을 끝낸다.

## D1 방법 선택

- as-is(I3)가 닫히기 전에는 방법을 확정하지 않는다. 현행을 보지 않은 to-be가 된다.
- 제약이 방법을 정하면 방법 하나와 "왜 하나인가"를 쓴다. 정한 설계를 다시 비교하지 않는다.
- 후보 비교는 조사 뒤 중요한 선택이 남고 실제로 다른 접근이 둘 이상 성립할 때, 또는 금액·데이터·정책·계약처럼 잘못 고른 비용이 클 때만 한다.
  1. 후보를 보기 전에 비교 기준을 `record.md` D1 항목에 쓴다. 대목표와 검증 기준에서 나온 것이어야 한다.
  2. 접근마다 `byko-stack:proposer` 하나를 Agent 도구로 띄운다. 비교가 이 결과를 기다리므로 포그라운드로 띄운다(`run_in_background: false`, 기다림을 쓸 수 있는 세션에서). 진행 보고로 턴을 끝내지 않는다. 메시지: `brief.md` 경로, 맡을 접근 한 줄, 1의 비교 기준, 대상 commit, 결과 파일 `candidate-<n>.md`. 다른 후보와 작성자의 선호는 주지 않는다. 후보끼리 끌려가지 않게 하려는 것이다.
  3. 후보가 모두 돌아온 뒤에 방법·근거·단점·실패 조건·검증 접근을 사전 기준으로 비교한다. 모두 탈락할 수 있다. 수를 채우는 대안은 만들지 않는다. 고른 것과 버린 것의 이유를 `record.md`에 쓴다.
- 후보 작성자는 자기 후보를 고르지 않는다. 선택은 메인이 한다.

## D2 검증 기준

구현 전에 `brief.md`에 쓰고 기준 commit과 시각을 붙인다. 구현 뒤 소급 작성과 가르기 위해서다.

| 축 | 쓰는 것 |
|---|---|
| as-is | 코드·정책·실제 값. 값이 실행에 달렸으면 재현 |
| to-be | 바뀌어야 하는 동작 |
| 보존 | 지켜야 할 기존 동작·정책·데이터·성능, 리포 사이 계약 |
| 옳은지 모르는 현행 | 현재 동작을 곧 옳은 정책으로 보지 않는다. 조사 질문이나 정책 질문으로 남긴다 |
| 적대·엣지 | 오류·경계값·동시성 |
| 환경 제약 | 실행할 수 없는 확인은 따로 표시한다 |

- 확인마다 조건 → 관찰 가능한 기대("~하면 ~가 나온다"), 기대의 출처(목적·정책·계약), 방법을 쓴다. happy path만 있는 기준은 구현자에게 나머지를 안 해도 된다는 신호가 된다.
- 기준이 닿을 곳은 변경마다 다르다. 데이터 구조, 외부 연동, 실패 처리, 권한, 마이그레이션·백필, 관측, 배포·되돌리기 같은 곳을 이 변경에 닿는지 보고, 닿지 않으면 쓰지 않는다.
- 리포의 기존 검사(테스트·린트·타입·실행 방법)를 먼저 쓴다. 관찰 방법을 새로 만들면 그것도 실제로 실행할 대상으로 적는다.
- 구현 뒤 새 위험은 '구현 후 보강'에 더한다. 기대값을 구현에 맞춰 낮추지 않는다. 기준을 바꿔야 하면 원래 근거와 대조한 이유를 `record.md`에 쓴다.

## D3 설계 검증

- 먼저 `design.md`를 쓴다. 고른 방법, 그 이유(후보 비교가 있었으면 고른 것과 버린 것), `brief.md` 검증 기준의 위치를 담는다. 자기 판정·자체 확인 결과는 넣지 않는다. 검토자가 이 파일과 `brief.md`를 읽는다.
- Skill 도구로 `review-run`을 부른다. 인자: `brief=<brief.md 경로> target=<design.md 경로와 대상 commit> kind=설계 검증 stance=문제 적합 lens=<목표 적합, 기준의 판별력, as-is 보존 누락 + 민감 축 관점> out=<review-design-*.md>`. 부른 턴에서 기다린다. 기준 자체도 검토 대상이다.
- `review-run`이 오류를 내거나 같은 턴에 결과가 오지 않으면 Agent 도구로 `byko-stack:reviewer`에 같은 인자를 맡기고, `record.md` '진행 중 위임'에 D3를 막는 항목으로 적는다. 결과 전에는 M1을 열지 않는다.
- 첫 검토자에게는 `brief.md`, `design.md`, 관점만 준다. 작성자의 확신·예상 판정은 주지 않는다. 고른·뺀 관점과 생략·축소 사유는 `brief.md` 선택·생략 사유에 써서 검토자가 함께 보게 한다.
- 지적마다 채택·기각·보류와 이유를 `record.md`에 쓰고, 근거 부족이면 I로, 목표 오독이면 G로, 정책 미결이면 사람에게 돌린다.
- 가벼움이면 D3를 사유와 함께 V2에 합친다. 그 V2 위임에는 `weight=가벼움`과 `evidence=`를 넣어 검토 깊이 경계가 함께 넘어가게 한다(`review`의 '맡기기').

ADR 같은 리포 설계 문서는 리포 규약이나 요청이 있을 때만 리포의 위치·형식으로 쓴다.
