# 스펙 챕터별 내용 규칙

골격은 `byko-doc new --kind spec`이 만든다. 마크업은 `shared/doc-snippets.md`, **완성된 실물은 `examples/spec-example.html`**. 이 문서는 **각 챕터에 무엇을 쓰는가**를 정한다.

스펙은 두 독자를 동시에 만족시켜야 한다. **사람**은 "이 방향이 맞나"를 몇 분 안에 판단하려 하고, **구현 에이전트**는 추가 질문 없이 착수할 수 있어야 한다. 앞의 요구가 문서 구조(챕터·스토리·악센트)를, 뒤의 요구가 상세도를 정한다.

## 챕터별로 무엇을 쓰나

| 챕터 | 내용 | 흔한 실패 |
|------|------|----------|
| **표지** | 제목(장면형 두 줄), 이 문서가 어떤 여정인지 한 문단, 진입 버튼, **끝까지 기억할 단어 2~3개** | 제목이 프로젝트 코드명 |
| **0. 한 문장** | "A를 B로 바꾼다" 결론 한 문장 + 지금까지 무엇이 불편했는지 + **이 문서에서 확정하지 않는 것** | 결론을 마지막에 두기 |
| **1. 개념** | 이 스펙을 읽는 데 필요한 단어 2~4개를 **실물에 빗대어** 정의 (`.terms`) | 코드 이름·클래스명부터 던지기 |
| **2. 현재 구조** | 관련 구성요소가 각각 무엇을 책임지나 (`.map` + `code-ref`). 어느 도메인이 이미 원하는 눈금으로 일하는지 | 아키텍처 전체를 그리기 |
| **3. 정상 흐름** | 문제 없는 경우 한 건을 **번호 단계로** 따라가기 (`.story`). 인물·수량을 세워 구체적으로 | 추상적인 "요청이 처리된다" |
| **4. 막히는 지점** | 같은 흐름을 문제 조건으로 다시 따라가기 (`.story.problem`) + **근본 원인 한 문장** | 증상만 나열하고 원인 없음 |
| **5. 바꾸는 것** | 전/후 대비(`.beforeafter`) + 바뀐 뒤의 흐름(`.story.fix`) | 구현 디테일부터 쏟기 |
| **6. 결정할 것** | 사람이 정해야 하는 것만 악센트 블록으로. 각각 **무엇을·왜·검토한 대안** | 모든 변경을 악센트로 달기 |
| **7. 완성 조건** | 상황을 눌러 보는 시나리오(`.scenario`). 전체 AC 표는 접어 둔다 | AC 표만 덜렁 두기 |
| **8. 만드는 순서** | 되돌릴 수 있는 것부터. 되돌릴 수 없는 단계를 명시(`.pipeline`) + 테스트가 따를 기존 패턴 | 순서의 기준을 안 밝히기 |
| **9. 기억할 것** | 이 도메인을 다음에 만질 때의 원칙 2~4개 (`.terms cols-2`) | 요약을 반복하기 |

현행 분석은 별도 장으로 늘어놓지 말고 **2장과 3장에 근거(`파일:라인`)로 녹인다.** 상세는 `analysis/<topic>.md`에 있고, 스펙은 판단에 필요한 만큼만 인용한다.

## AC 작성

- "~가 동작한다" (X) → "~를 입력하면 ~가 반환된다" (O). 관찰 가능한 입력과 결과로
- 각 AC에 검증 방법 (unit / integration / 동시성 / 수동 확인)
- **에러·경계값·동시성 AC를 빠뜨리지 않는다.** happy path만 있는 AC는 구현자에게 "안 해도 된다"는 신호가 된다
- 7장 시나리오 탭은 AC와 1:1로 맞춘다 — 탭 하나가 AC 하나이고, 탭 아래에 `<span class="scn-ac">AC-1</span>`로 표기한다

## 악센트를 어디에 다나

판단 기준은 하나다: **잘못 정하면 나중에 비싸게 되돌려야 하는가, 그리고 그 판단이 유저의 몫인가.**

| 표시한다 | 표시하지 않는다 |
|---------|----------------|
| 처음 생기는 도메인 용어 (`new`) | 이미 코드베이스에 있는 용어를 그대로 쓰는 것 |
| 새 타입·스키마·인터페이스 (`type`) | 기존 타입에 선택 필드 하나 추가 |
| 마이그레이션·백필·저장 포맷 (`data`) | 코드 내부 자료구조 변경 |
| 유저 확인 없이 정한 것 (`decision`) | 유저가 이미 확답한 것 |
| 공개 API·보안·비용·외부 계약 (`risk`) | 되돌리기 쉬운 내부 변경 |
| `[TBD]`·blocking (`open`) | 구현 중 정하면 되는 세부 |

ledger의 `assumed` → `decision`, `open`/`blocking` → `open`으로 1:1 대응시킨다. 유저가 스펙 하나만 보고도 확인해야 할 것을 전부 만나게 된다.

악센트 블록에는 **무엇을 정했는지 + 왜 + 검토했던 대안과 기각 이유**를 함께 쓴다. 대안이 보여야 유저가 뒤집을지 판단할 수 있다.

## 멀티 스펙

독립 기능 3개 이상이고 도메인이 서로 다르면 분할을 제안한다.

```
docs/specs/<project>/
├── index.html          # 현황 (manifest에서 생성)
├── spec.html           # 메인 — 전체 목표, 서브 스펙 관계, 공통 규칙
└── sub-specs/
    ├── 01-<feature>.html
    └── 02-<feature>.html
```

- 메인 스펙: 0~2장(한 문장·개념·현재 구조)을 공통으로 두고, **서브 스펙 진행 현황 표**(경로·설명·상태·의존)를 더한다
- 서브 스펙: 같은 챕터 골격. 표지의 진입 버튼에 메인 스펙 링크를 넣는다
- `byko-doc new --kind spec --out .../sub-specs/01-<feature>.html --workdir docs/specs/<project>` — `--workdir`을 주면 상위 `assets/`를 상대 경로로 연결한다
- 서브 스펙이 완료될 때마다 메인의 현황 표와 매니페스트를 갱신한다

## 작성 원칙

- 한국어로 쓰되 코드·기술 용어는 영어를 유지한다
- 구현자(사람 또는 에이전트)가 읽고 바로 착수할 수 있을 만큼 구체적으로
- 추측하지 않는다 — 확실하지 않으면 유저에게 묻거나 `open` 악센트로 남긴다
- **사소해 보이는 사실을 버리지 않는다.** 구현할 때 필요한 조건·제약은 본문에 남기고, 판단이 필요 없는 것만 접어 둔다
- 대화에서 결정된 사항은 즉시 반영하고, 고칠 때마다 `build` → `check`

## 중단 후 재개

`manifest.md`와 `ambiguity-ledger.md`로 현황을 복원한다: ledger 게이트 상태 확인 → `spec.html` 6장의 결정 목록으로 남은 판단거리 확인 → 유저에게 요약하고 다음 단계 제안.
