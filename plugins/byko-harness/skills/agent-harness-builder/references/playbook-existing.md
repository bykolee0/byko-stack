# 기존 개발 리포

코드·테스트·CI가 있지만 이 하네스는 없는 리포다. 이 스킬의 이전 판이 만든 옛 형태의 하네스가 있는 리포도 여기서 다룬다. 지식은 대부분 코드와 기존 문서에 흩어져 있으니 먼저 읽고, 근거가 있는 것만 정의로 올린다.

- **보완(기본):** 기존 파일은 그 자리에 두고, 빠진 것만 채워서 색인으로 연결한다.
- **정렬:** 사용자가 "기존 문서도 이 구조로 맞춰 달라"고 요청했을 때만 한다. 보완을 한 뒤 기존 문서를 옮긴다.

## 1. 훑기

- 진입 문서: AGENTS.md(하위 폴더 것까지: `git ls-files '*AGENTS.md'`), CLAUDE.md(그 안의 `@` 가져오기), README, CONTRIBUTING, docs/
- 매니페스트와 잠금 파일, 테스트 구성(러너, 경고 처리 같은 설정), lint·format 설정, CI 설정, 배포·인프라 흔적(Dockerfile, IaC, 배포 스크립트)
- 기존 결정·작업 기록 폴더: adr/, specs/, plans/, rfcs/ 등
- 옛 하네스의 흔적: docs/README.md, docs/design-docs/, docs/exec-plans/, docs/generated/
- docs/의 쓰임: 문서 사이트의 원본(Sphinx, MkDocs, Docusaurus 등)인지, 배포 패키지에 들어가는지. 설정 파일과 패키지 포함 목록으로 본다.
- 최상위 영역(모듈·서비스·패키지)과 각각의 크기

이 단계에서 리팩터하지 않는다. 언어, 테스트 도구, 아키텍처는 추측으로 확정하지 않고 파일로 확인한다.

## 2. 분석

리포가 커서 메인이 다 읽기 어렵고 내용이 영역별로 나뉘면 영역별 분석을 나눠 맡긴다([analysis.md](analysis.md)). 그렇지 않으면 직접 읽는다. 어느 쪽이든 모을 것은 같다.

- **정책 후보:** 규칙 문장, 근거 위치(`파일:줄`), 근거끼리 맞는지
- **도메인 개체·용어와 그 관계**
- **영역을 넘는 흐름:** 이벤트·큐, 호출, 데이터 이동. 매 세션 다시 파게 되는 연결이 여기다.
- **실행·테스트·배포 사실:** 명령, 환경 변수, 외부 의존
- **코드에서 보이지 않는 전역 관례:** 문서·설정·리뷰 규칙에만 있는 것
- **반복된 실수:** 되돌린 커밋, 같은 곳을 거듭 고친 이력, 리뷰 규칙에 드러난 것. 제약형 정책과 강제 검사의 좋은 후보다.
- **충돌, 그리고 보지 못한 곳**

## 3. 정책으로 올리는 기준

정책은 이 리포에서 지켜야 하는 규칙이다. 어기면 버그·보안·데이터·호환성·계약 문제가 된다. 구현 세부를 옮겨 적은 것은 정책이 아니다.

- **근거가 여럿이고 서로 맞는 경우:** `from-code`로 쓴다. 예: 코드와 테스트와 문서가 같은 규칙을 말한다.
- **근거가 한 곳뿐인 경우:** 그것이 규칙으로 의도된 것임이 드러나면 `from-code`로 쓰고, `sources`에 그 한 곳을 적는다.
  - 의도가 드러나는 단서: 이름 붙은 상수, 검증 코드, 오류 메시지, 테스트, 주석·문서.
  - 값만 있고 의도의 단서가 없는 구현 세부는 정책으로 올리지 않는다.
- **근거끼리 다른 말을 하는 경우:** 정책으로 쓰지 않는다. 예: 문서는 14일, 코드는 30일. AGENTS.md "미결정"에 무엇과 무엇이 어떻게 다른지와 근거 위치를 올린다.
  - 사람이 대화에 있으면 그 목록을 묻는다(SKILL.md 원칙 7).
- **정책 페이지의 범위:** 정책 하나에 페이지 하나가 아니다. 관련된 규칙을 영역별로 묶는다(예: 보안, 호환성, 변경 절차). 그래야 색인이 짧고 찾기 쉽다.

## 4. 정리

- **domain·architecture:** 코드만 읽어서는 매번 다시 파야 하는 연결을 정의로 쓴다. 파일 배치를 옮겨 적지 않는다.
- **infrastructure·deploy·testing:** 코드 밖의 실행 지식만 쓴다. 명령 줄은 AGENTS.md "명령"에 두고, 페이지는 이름으로 가리킨다.
- **하네스의 위치:** [structure.md](structure.md)의 "놓는 자리"를 따른다. docs/가 문서 사이트의 원본인 리포가 많다.
- **기존 문서와의 관계(보완 모드)**
  - **기존 AGENTS.md:** 내용을 지우지 않는다. 빠진 절을 더하고 색인을 붙인다.
    - 긴 설명이 있으면 지우지 말고, 보고에 "wiki로 옮길 후보"로 적는다.
    - 크기 상한(32KiB)을 넘으면 Codex가 뒷부분을 읽지 못한다. 이때는 세부 절을 wiki 페이지로 옮기는 것까지 보완에 넣는다. 문장은 바꾸지 않고 옮긴다.
  - **기존 CLAUDE.md:** 맨 위에 `@AGENTS.md`가 없으면 더한다. 내용은 옮기지 않는다. Claude 전용이 아닌 공통 지침은 Codex가 읽지 못하므로, 보고에 "AGENTS.md로 옮길 후보"로 적는다. 옮기는 일은 정렬 모드에서 한다.
  - **하위 폴더의 AGENTS.md:** 그대로 둔다. 옆에 CLAUDE.md가 없으면 `@AGENTS.md`만 담은 CLAUDE.md를 더한다. 루트에 CLAUDE.md가 있으면 Claude Code가 하위 AGENTS.md를 읽지 않기 때문이다([structure.md](structure.md) "CLAUDE.md와 하위 폴더").
  - **CONTRIBUTING이나 규칙 문서:** 정책의 근거로 쓰고, 색인에서 가리킨다.
  - **기존 결정·작업 기록 폴더:** 그 위치를 records로 삼는다. AGENTS.md 색인과 문서 규격 블록의 경로도 그 위치로 적는다. 같은 역할의 새 폴더를 따로 만들지 않는다.
  - **기존 외부 자료:** references/index.md에 싣거나, 원래 위치를 색인에서 가리킨다.

## 5. 정렬 모드에서 더 할 일

옮길 목록(원래 위치 → 새 위치, 이유)을 먼저 만든다. 사람이 대화에 있으면 확인받고, 없는 실행이면 요청이 정렬을 분명히 말한 경우에만 옮긴다. 옮길 때는 `git mv`로 이력을 남긴다.

| 원래 | 새 위치 |
|---|---|
| ADR·스펙·계획·옛 `docs/design-docs/`·`docs/exec-plans/`·`docs/specs/` | `docs/records/YYYY-MM-DD-<종류>-<제목>.md`. 날짜는 문서 안의 날짜나 git의 최초 커밋 날짜를 쓴다 |
| 그 기록들 가운데 지금도 유효한 결정 | wiki 정의로 쓰고, `sources`가 옮긴 기록을 가리킨다 |
| 옛 `docs/generated/` | `docs/references/`로 옮기고 index에 만드는 명령을 적는다 |
| 옛 `docs/README.md`(문서 지도) | 내용을 AGENTS.md 색인과 폴더 index로 나눠 담은 뒤, 원본은 `git mv`로 records로 옮긴다 |
| CLAUDE.md의 공통 지침 | AGENTS.md로 옮긴다. 문장은 바꾸지 않는다. CLAUDE.md에는 `@AGENTS.md`와 Claude 전용 내용만 남긴다 |
| 설명형 문서(아키텍처 설명 등) | "## 정의"로 시작하는 wiki 페이지로 바꾼다. 원문에서 지금도 맞는 정의만 남기고 나머지는 부차 절로 내린다. 원본은 records로 옮겨 근거로 둔다 |

옮긴 경로를 가리키던 링크를 고친다. 지운 내용이 없는지 git으로 확인한다.

## 6. 검사와 검토

- 리포의 test 도구로 하네스 규격 검사를 만들고 실행한다([checks.md](checks.md)). 리포의 테스트 설정(경고를 오류로 다루는지 등)과 lint 규칙에 맞게 쓴다.
- `from-code` 정책 가운데 지금 테스트로 막을 수 있는 것은 강제 검사를 만든다.
- 기존 테스트와 lint를 돌려 깨진 것이 없는지 확인한다. 실행할 수 없는 환경이면 그렇다고 보고하고, 처음 돌릴 명령을 적는다.
- 정의와 `sources`를 대조하는 독립 검토를 한 번 받는다([analysis.md](analysis.md)의 검토 지시). 지적이 사실이면 고친다.
