# 하네스 유지

이 하네스가 이미 있는 리포에서 지금 상태에 맞춘다. 낡은 정의가 가장 큰 위험이다. 에이전트는 문서와 코드가 어긋나도 문서를 따르기 쉽기 때문이다. 그래서 "무엇이 바뀌었나"를 git으로 좁혀서 그 부분만 다시 확인한다.

## 기준점

- **페이지별 낡음:** 각 페이지의 `verified`를 기준으로 본다(아래 2).
- **새 기록과 정책 위반:** "마지막 유지 이후"를 기준으로 본다. 다음 순서로 정한다.
  1. records에 남긴 마지막 하네스 유지 기록을 더한 커밋
  2. 그것이 없으면, wiki 페이지들의 `verified` 가운데 가장 오래된 것. 가장 최근 것을 쓰면 다른 작업이 한 페이지의 `verified`만 올린 경우 그 사이에 더해진 결정 기록을 놓친다.
  3. 그것도 없으면, 하네스 파일(AGENTS.md, wiki, references)을 마지막으로 바꾼 커밋: `git log -1 --format=%h -- AGENTS.md <wiki 경로> <references 경로>`
- `verified`의 커밋을 git이 찾지 못하면(스쿼시 머지로 사라진 경우 등) 그 날짜로 대신 본다: `git log --since=<날짜>`.

## 1. 형식 확인

- 하네스 규격 검사와 정책 강제 검사를 실행한다.
- 형식 문제는 고친다: 필드, 링크, 색인. 색인에 없는 파일은 지우지 않고 색인에 싣는다.
- 정책 강제 검사가 코드 때문에 실패하면(정책 위반) 코드도 규칙도 검사도 고치지 않는다. 코드가 틀렸는지 정책이 낡았는지는 판단이 필요하기 때문이다. 처리는 [checks.md](checks.md)의 "위반이 나왔을 때"를 따른다.
  - 통과하던 검사가 기준점 이후의 변경으로 실패하면, 그 커밋과 어긴 정책을 보고의 맨 앞과 미결정에 올린다. 검사는 실패한 채로 두고 "기존 위반" 목록에 넣지 않는다.
  - 이 환경에서 검사를 실행할 수 없으면, 기준점 이후 바뀐 코드를 정책 페이지와 강제 검사의 내용에 비춰 읽고 위반으로 보이는 것을 같은 방식으로 보고한다.

## 2. 낡은 정의 찾기

wiki 페이지마다 다음 순서로 본다.
1. 확인 이후 `scope` 경로가 바뀌었는지 본다.
   - `verified`에 커밋이 있으면: `git log --oneline <커밋>..HEAD -- <scope 경로들>`
   - 날짜만 있거나 커밋을 찾지 못하면: `git log --oneline --since=<날짜> -- <scope 경로들>`
   - `scope`가 기능 이름뿐이라 경로를 정할 수 없으면 `sources`의 경로로 본다.
2. 바뀐 페이지는 정의를 코드·문서·테스트와 다시 대조한다.
3. 대조 결과에 따라 처리한다. 기준은 정의마다 그 근거가 어디서 왔는가다.
   - **정의가 여전히 맞으면:** `verified`만 갱신한다.
   - **코드 현황을 옮겨 적은 부차 설명만 틀렸으면:** 코드에 맞춰 고친다.
   - **근거가 리포 안의 자료이고, 그 자료가 새 동작으로 일관되게 바뀌었으면:** 정의를 새 동작으로 고친다. 예: `from-code` 정책, 코드에서 정리한 domain·architecture 정의. 코드·문서·테스트가 함께 바뀐 경우가 이렇다. `sources`에 바뀐 근거를 적는다.
   - **근거가 사람의 결정이면(`confirmed`, 결정 기록을 가리키는 정의):** 코드가 달라도 정의를 고치지 않는다. 코드가 틀렸을 수 있기 때문이다. AGENTS.md "미결정"에 무엇이 어떻게 다른지와 근거를 올린다.
   - **자료끼리 엇갈리면:** 예를 들어 코드는 바뀌었는데 문서·테스트는 그대로다. 정의를 고치지 않고 미결정에 올린다.

## 3. 페이지끼리의 모순

같은 대상을 여러 페이지가 말하면 서로 맞는지 본다. AGENTS.md와 wiki 사이도 본다. 예: 정책은 14일, domain 정의는 30일.
- 한쪽이 사람의 결정이면 그쪽에 맞춘다.
- 둘 다 리포 자료에서 왔으면 위 2의 기준으로 지금 근거를 다시 본다.
- 정할 수 없으면 미결정에 올린다.

## 4. 새 기록 반영(ingest)

- 기준점 이후 records·references에 더해진 파일을 git log로 찾는다. 이미 어느 페이지의 `sources`가 가리키는 기록은 반영된 것이다.
- 새 결정이 정의를 바꾸면 해당 페이지를 고치고, 그 정의에서 기록을 가리키고 `sources`에도 더한다.
  - 페이지의 규칙이 모두 사람의 결정이면 `confirmed`, 코드에서 정리한 규칙과 섞이면 `from-code`로 둔다([structure.md](structure.md)의 `status`).
  - 결정이 코드에 아직 반영되지 않았으면 미결정에 "결정과 코드 불일치"로 올린다.
- 새 references 파일이 index에 없으면 싣는다.

## 5. AGENTS.md 확인

- 색인이 가리키는 경로가 있는지 본다.
- "명령"에 적힌 명령이 아직 존재하는지 본다. 매니페스트 스크립트, Makefile, CI에서 확인한다. 배포 명령은 실행하지 않는다.
- 크기 상한을 넘지 않는지 본다.
- 미결정 항목 가운데 해결된 것이 있으면 결정 기록을 남기고 그 항목을 지운다.
- 하위 폴더에 새 AGENTS.md가 생겼으면 옆에 CLAUDE.md가 있는지 본다([structure.md](structure.md) "CLAUDE.md와 하위 폴더").

## 6. 마무리

- 검사를 다시 실행한다. 하네스 규격 검사는 통과해야 한다. 기준점 이후 생긴 정책 위반으로 실패하는 강제 검사만 예외이고, 보고의 맨 앞에 둔다.
- records에 하네스 유지 기록(`YYYY-MM-DD-work-harness-maintenance.md`)을 남긴다. 다음 유지의 기준점이 된다.
- 보고에 담을 것
  - 고친 형식 문제
  - 갱신한 정의와 그 근거
  - 새로 생긴 미결정과 정책 위반
  - 확인하지 못한 페이지
