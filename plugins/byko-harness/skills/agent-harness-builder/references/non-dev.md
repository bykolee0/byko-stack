# 개발이 아닌 리포

책·교재, 연구 노트, 운영 문서, 데이터 정리처럼 코드가 중심이 아닌 리포다. 정해진 절차를 따르기보다, 아래 원리를 이 리포에 맞게 옮겨서 구성한다. 개발 리포와 같은 층을 쓰는 이유는 문제가 같기 때문이다. 에이전트가 매번 다시 찾지 않게 최종 정의를 한곳에 두고, 항상 로드되는 곳에서 가리키고, 형식은 검사로 지킨다. LLM Wiki도 개인 연구, 독서, 팀 문서처럼 도메인을 가리지 않는다.

## 층은 그대로 쓴다

- **AGENTS.md:** 이 리포가 무엇이고 무엇을 위한 것인지, 색인, 지켜야 할 규칙, 문서 규격, 빌드·확인 명령, 미결정.
- **docs/wiki:** 이 리포의 최종 정의. 정책이 중추다.
- **docs/records:** 결정과 작업 기록.
- **docs/references:** 원자료와 참고 자료. 반드시 index를 둔다.
- 이 층이 이미 다른 이름으로 있으면 이름을 바꾸지 않고 색인으로 연결한다. 예: 용어집·정의를 모은 `notes/`는 wiki 역할, 원자료를 모은 `sources/`는 references 역할이다. 그 실제 경로를 AGENTS.md "문서 규격" 블록과 검사의 경로 상수에 적는다. 블록과 검사가 기본 경로를 말하면 다음 에이전트가 없는 폴더를 찾는다.
- 원고·결과물 폴더(`chapters/` 등)는 개발 리포의 코드처럼 산출물이다. 하네스 층이 아니므로 프론트매터나 "## 정의"를 넣지 않는다.
- docs/가 출판이나 문서 사이트의 원본이면 하네스 파일이 공개되지 않게 위치를 정한다([structure.md](structure.md) "놓는 자리"). 개발이 아닌 리포에서 특히 흔하다.
- 정책 상태도 같은 두 값을 쓴다. 여기서 `from-code`는 리포 안의 자료(원고, 설정, 빌드 스크립트, 기존 문서)를 근거로 정리했다는 뜻이다. 이름을 바꾸지 않는 것은 검사가 같은 값을 보기 때문이다.

## 페이지는 질문으로 정한다

아래 질문에 답이 있는 것만 페이지로 만든다.

1. 여기서 최종 정의(SSOT)는 무엇인가? 용어집, 등장인물·개념, 데이터 사전, 운영 기준 같은 것이다.
2. 반드시 지켜야 할 규칙은 무엇인가? 문체, 표기, 인용, 공개 범위, 라이선스, 개인정보 같은 것이다. 이것이 정책이다.
3. 에이전트가 매번 다시 찾게 되는 것은 무엇인가? 전체 구성, 장 사이의 연결, 자료의 출처 관계 같은 것이다.
4. 결과물은 무엇으로 확인하는가? 빌드, 링크 검사, 맞춤법·용어 검사, 미리보기 같은 것이다.

개발 리포의 페이지와는 이렇게 대응시켜 생각하면 된다. 이름은 리포에 맞게 정한다.

| 개발 리포 | 개발이 아닌 리포의 예 |
|---|---|
| domain.md | 용어집, 개념·인물 정의, 데이터 사전 |
| architecture.md | 산출물의 구조(장 구성, 문서 체계), 원자료에서 결과물까지의 흐름 |
| testing.md | 결과물을 확인하는 방법(빌드, 검증 게이트, 검수 기준) |
| deploy.md | 내보내기·출판·공유 절차 |
| infrastructure.md | 쓰는 도구와 환경(빌드 도구, 저장소, 외부 서비스) |

## 검사

- 리포에 이미 빌드나 검증 게이트가 있으면, 하네스 규격 검사를 그 게이트에 붙인다([checks.md](checks.md)).
- 게이트가 없으면 새 도구를 들이지 않는다. "검사 미정"을 미결정에 올리고 "기초만 됨"으로 보고한다.
- 꼭 지킬 규칙이 기계로 확인 가능하면 검사로 만든다. 금지어, 필수 표기, 링크 같은 것이다.

이 문서는 출발점이다. 개발이 아닌 리포의 구성은 쓰면서 고도화한다.
