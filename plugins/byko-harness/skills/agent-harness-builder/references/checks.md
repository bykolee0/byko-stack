# 검사

검사는 두 종류다. 하네스 규격 검사는 문서가 규격을 지키는지 보고, 정책 강제 검사는 코드가 꼭 지켜야 할 정책을 지키는지 본다. 둘 다 리포가 이미 쓰는 test 도구 안에 만든다. 규칙을 글로만 두면 에이전트도 사람도 건너뛸 수 있지만, 테스트가 실패하면 그 자리에서 고치게 된다.

## 하네스 규격 검사

검사할 것:
1. **wiki 프론트매터:** 모든 wiki 페이지에 `title`, `summary`, `scope`, `sources`, `verified`가 있다. `sources`와 `scope`는 비어 있지 않다. `verified`는 `YYYY-MM-DD`이고, 뒤에 짧은 커밋 해시가 올 수 있다(커밋이 있는 리포는 붙인다).
2. **정책 필드:** policies 아래 페이지는 `status`가 `confirmed`나 `from-code` 중 하나이고, `enforced_by` 키가 있다(빈 목록도 된다).
3. **정의가 맨 위:** 본문의 첫 `## ` 절이 정의 제목(기본 `## 정의`)이다.
4. **색인 일치:** wiki의 하위 폴더(policies/ 포함)와 references/의 모든 파일이 그 폴더 index.md에 링크로 실려 있다. index.md의 링크가 가리키는 파일도 모두 있다.
   - wiki의 하위 폴더는 모두 자기 index.md가 있어야 한다. references의 하위 폴더는 index.md를 둘 수 있다.
   - 하위 폴더에 자기 index.md가 있으면 그 폴더의 파일은 그 index.md가 싣고, 그 index.md(또는 폴더)는 위 폴더의 색인이 싣는다. 어디서도 가리키지 않는 색인은 찾히지 않는다.
5. **AGENTS.md 색인:** wiki 루트의 페이지와 폴더, 그리고 references를 AGENTS.md가 링크로 가리킨다. 폴더는 index.md나 폴더 자체를 가리키면 된다. 항상 로드되는 색인에 없는 영역은 에이전트가 찾지 않는다.
6. **근거 경로:** `sources`, `enforced_by`의 리포 경로가 실제로 있다. URL은 제외한다. 경로는 리포 루트 기준이며 앞의 `/`는 무시한다. `경로::이름`, `경로#절`, `경로:줄`, `경로:시작-끝`은 경로만 본다.
7. **AGENTS.md:** 파일이 있다. 32KiB를 넘지 않는다. 마크다운 링크가 가리키는 경로가 있다(코드 블록과 인라인 코드 안의 예시 링크는 빼고 본다). 200줄 이상이면 실패시키지 않고 알리기만 한다. 경고를 오류로 다루는 테스트 설정(pytest `filterwarnings = error` 등)에서도 실패하면 안 되고, 알림은 보여야 한다. Python 예시는 그 경고에만 오류 설정을 풀어 경고 요약에 남긴다.
8. **CLAUDE.md:** AGENTS.md가 있는 폴더에 CLAUDE.md가 있으면, 코드 블록과 인라인 코드 밖에 `@AGENTS.md`(또는 `@./AGENTS.md`)가 있다. 루트에 CLAUDE.md가 있으면 하위 폴더의 AGENTS.md 옆에도 그런 CLAUDE.md가 있다. 그렇지 않으면 Claude Code는 그 AGENTS.md를 읽지 않는다([structure.md](structure.md) "CLAUDE.md와 하위 폴더").
9. **경로 상수:** AGENTS.md가 검사의 wiki 경로를 말한다. 검사 파일의 경로 상수가 리포의 문서 규격과 다르면 검사가 빈 곳을 보고 아무것도 없이 통과하기 때문이다.

검사하지 않는 것:
- 정의가 실제와 맞는지. 판단이 필요하니 유지 작업과 독립 검토에서 본다.
- records의 형식. 관리 의무가 없는 로그다.

## 실패 메시지

메시지에는 다음 네 가지를 담는다.
- 무엇을 어겼나
- 어디서 어겼나
- 왜 중요한가
- 어떻게 고치나: AGENTS.md "문서 규격" 절을 가리킨다

예:
```
docs/wiki/policies/refund.md: 'verified'가 비어 있거나 없다
왜: 확인 시점이 없으면 이 정의가 낡았는지 알 수 없다
고치는 법: AGENTS.md의 '문서 규격' 절을 보고 필드를 채운다
```

정책 강제 검사의 "어떻게 고치나"는 문서 규격이 아니라 그 정책 페이지를 가리킨다. 실패를 본 에이전트가 규칙의 이유와 범위를 그 자리에서 읽게 하기 위해서다.

## 언어별로 만들기

- **Python(pytest):** [examples/python/test_harness_docs.py](../examples/python/test_harness_docs.py)를 리포의 테스트 폴더에 둔다. 설정 상수(경로, 정의 제목)를 맞춘다. 리포 문서가 영어면 `GUIDE`와 메시지도 영어로 옮긴다. `GUIDE`는 AGENTS.md에 실제로 있는 절 이름을 가리켜야 한다. 표준 라이브러리만 쓴다.
- **Python(unittest):** 같은 파일의 `test_` 함수들을 `unittest.TestCase` 클래스의 메서드로 옮긴다. unittest는 맨 함수를 모으지 않는다.
- **Node(node:test):** [examples/node/harness-docs.test.mjs](../examples/node/harness-docs.test.mjs)를 테스트 폴더에 두고, 리포의 test 스크립트가 실행하게 한다. 의존성이 없다.
- **Node(vitest·jest):** 이 러너들은 `node:test`의 `test`를 자기 테스트로 세지 않는다. vitest의 기본 수집 규칙은 `.test.mjs`도 모으므로, 그대로 두면 이 파일에서 테스트를 찾지 못한다. `node:test` 가져오기를 러너의 `test`로 바꾼다(vitest는 `import { test } from "vitest"`, jest는 전역 `test`). `node:assert`는 그대로 쓴다. 모듈 형식(ESM·CJS·TS)과 파일 이름은 러너의 설정에 맞춘다.
- **그 밖의 언어:** 위 예시의 규칙을 리포 테스트 도구로 옮긴다. 파일 읽기와 정규식이다. 예시가 처리하는 경우를 함께 옮긴다: BOM과 CRLF, 점으로 시작하는 폴더(`.obsidian` 등), macOS의 NFD 한글 파일 이름, 경로 상수 끝의 `/`. 테스트 도구가 여럿인 다언어 리포는 리포가 이미 쓰는 공용 검사 명령(Makefile, task runner)에 붙인다.
- 리포에 테스트 도구가 없으면 새로 들이지 않는다. 미결정에 올리고 "기초만 됨"으로 보고한다.
- 리포의 테스트 설정과 lint 규칙(경고 처리, 타입 검사, 파일 이름 규칙)에 맞춘다. 새 검사가 다른 게이트를 깨면 완료가 아니다.

예시는 루트를 위로 올라가며 찾는다. `.git`이 있는 가장 가까운 폴더를 먼저 찾고, 없을 때만 AGENTS.md가 있는 폴더를 쓴다. 하위 폴더의 AGENTS.md를 루트로 잡으면 검사가 엉뚱한 곳을 보기 때문이다. 환경 변수 `HARNESS_ROOT`로 바꿀 수 있다.

## 정책 강제 검사

꼭 지켜야 하는데 위반을 기계로 알아낼 수 있는 정책만 만든다. 만들면 정책 페이지의 `enforced_by`에 경로를 적는다.

고르는 기준:
- 로컬에서 싸게 돈다.
- 결과가 늘 같다.
- 실패 원인이 분명하다.
- 리포의 기존 test·lint로 만들 수 있다.
- 실제 위험에 대응한다.

피할 것:
- 큰 재작성이 필요한 검사
- 매 실행마다 비싼 검사
- 아직 받아들이지 않은 도구
- 취향만 반영한 규칙

후보:
| 검사 | 막는 것 |
|---|---|
| 아키텍처 경계·의존 방향 | 금지된 계층 넘기, 도메인 코드가 프레임워크·DB 클라이언트를 직접 가져오기 |
| 이름·배치 | 합의한 파일·모듈 관례에서 벗어나기 |
| 시간·날짜 | 정책이 시간대 규칙을 정한 경우의 위반 |
| 외부 계약(fixture) | 외부 API 응답 모양이 바뀐 것을 모르고 지나가기 |
| 생성 자료 최신성 | references의 생성 자료(스키마 덤프 등)가 만드는 명령의 결과와 다른 것 |
| 비밀값 | 자격 증명이나 로컬 환경 값이 커밋되는 것. 실패 메시지에는 값을 쓰지 않고 위치만 쓴다 |

언어별 수단:
- Python: pytest 구조 테스트. 규칙이 커지면 import-linter.
- Node/TS: eslint 규칙, vitest·jest 테스트.
- Go: `go test` 안의 패키지 검사.
- Rust: `cargo test`나 xtask.

같은 실수가 반복되면 그 실수를 검사로 만든다. 새 검사가 실제 그 실수에서 실패하는지 한 번 확인한다.

### 위반이 나왔을 때

어느 경우든 그 자리에서 코드를 고치지도, 규칙을 느슨하게 하지도 않는다. 위반이 버그인지 정책이 낡은 것인지는 판단이 필요하다.

- **검사를 처음 만들 때 코드가 이미 어기고 있으면(쌓여 있던 위반):** 위반을 검사 안의 "기존 위반" 목록에 명시해 검사가 통과하게 한다. 새 검사를 들이면서 게이트를 깨지 않기 위해서다.
  - 항목마다 위치와 이유를 적고, 정책 페이지를 가리킨다.
  - 목록에 없는 새 위반은 계속 실패하게 한다.
  - 목록은 줄어드는 방향으로만 바꾼다. 목록의 항목이 고쳐져 더는 위반이 아니면 검사가 그것도 알린다.
  - AGENTS.md "미결정"에 올리고 보고한다.
- **통과하던 검사가 새로 실패하면(나중에 생긴 위반):** 검사가 제 할 일을 한 것이다. 목록에 넣어 통과시키지 않는다. 그러면 검사가 막으려던 변경이 그대로 지나간다.
  - 어느 커밋이 무엇을 어겼는지 찾아 보고의 맨 앞에 둔다.
  - 미결정에 "코드를 되돌릴지, 정책을 바꿀지"로 올린다.
  - 사람이 대화에 있으면 바로 묻는다.
