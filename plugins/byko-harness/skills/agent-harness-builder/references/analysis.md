# 분석 나누기와 독립 검토

기존 리포의 지식은 영역마다 흩어져 있다. 한 컨텍스트로 다 읽으면 좁게 보다가 연결을 놓치거나, 넓게 읽다가 오래 걸린다. 영역별로 나눠 읽게 하고 메인이 합치면 둘 다 줄어든다. 다만 하위 에이전트는 비용이 들고 같은 일을 맡긴다고 답이 나아지지 않으니, 나눌 이유가 있을 때만 쓴다.

## 나눌지 정하기

기준은 영역의 수가 아니라 읽을 양이다. 훑기 단계에서 본 영역별 크기로 정한다.

- **나눈다:** 메인이 진입점·공개 인터페이스·테스트·설정을 다 읽으면 컨텍스트 대부분을 원문 읽기에 쓰게 되고, 그 내용이 영역별로 나뉠 때. 영역은 서비스, 패키지, 큰 모듈 같은 것이다.
- **직접 한다:** 메인이 다 읽을 수 있는 크기. 작은 패키지가 여럿인 리포도 여기다. 메인이 읽는 편이 빠르고 싸며, 연결도 한 손으로 본다.
- **흐름 담당을 하나 더 둔다:** 나누기로 했고, 이벤트 큐나 메시지 버스처럼 여러 영역을 잇는 중심 장치가 있으면, 그 흐름만 따라가는 분석을 하나 더 둔다.

## 도구

- 현재 호스트가 주는 하위 에이전트 도구를 확인해서 쓴다.
  - Claude Code: Agent 도구. 읽기 전용 탐색이면 Explore 에이전트.
  - Codex: 노출된 에이전트 생성 도구. 예: `spawn_agent`. 지원하는 인자만 쓴다.
- 이름이 같은 도구가 있다고 가정하지 않는다.
- 하위 에이전트를 쓸 수 없으면 같은 질문을 영역 순서대로 직접 한다.

## 위임 지시에 넣을 것

하위 에이전트는 이 스킬도, 리포의 AGENTS.md나 CLAUDE.md도, 대화도 보지 못할 수 있다. 판단에 필요한 것을 지시에 직접 담는다.

- 목적: 이 리포의 하네스(최종 정의 wiki)를 만들기 위한 근거 수집이라는 것
- 맡은 영역의 경로. 다른 영역은 연결을 확인할 때만 읽는다.
- 읽기 전용: 파일을 만들거나 고치지 않는다. 결과는 마지막 응답으로 돌려준다. 리포에 분석 파일이 남으면 다음 에이전트가 그것을 문서로 오해한다.
- 돌려줄 것: 아래 형식. 근거는 `파일:줄`로 단다. 메인이 그 줄을 바로 열어 확인할 수 있게 하기 위해서다.
- 멈출 때: 아래 질문에 답할 근거를 찾았거나, 진입점·공개 인터페이스·테스트·설정을 다 본 때. 다 못 본 곳은 "안 본 곳"에 적고 멈춘다.

## 돌려받을 형식

```markdown
# <영역> 분석
## 정책 후보
- 규칙 문장 — 근거 `파일:줄`(여러 개) — 일치: 코드·문서·테스트가 같은가(같음/다름: 무엇이 어떻게)
## 도메인 개체·용어
- 이름 — 정의 — 관계(무엇을 소유·발생·참조) — 근거
## 영역을 넘는 흐름
- 보내는 것/받는 것(이벤트, 호출, 데이터) — 상대 영역 — 근거
## 실행·테스트·배포
- 명령, 환경 변수, 외부 의존, 테스트 방식 — 근거
## 코드에서 보이지 않는 관례
- 문서·설정·리뷰 규칙에만 있는 것 — 근거
## 충돌·의문
## 안 본 곳
```

## 합치기

- 결과마다 핵심 근거 몇 개를 직접 열어 확인한다. 요약을 그대로 믿지 않는다.
- 같은 규칙이 영역마다 다르게 보고되면 충돌로 다룬다. 정책으로 쓰지 않고 미결정에 올린다.
- 흐름은 보내는 쪽과 받는 쪽 보고를 맞춰서 architecture 정의로 만든다.

## 독립 검토

wiki 정의를 다 쓴 뒤, 새 컨텍스트의 검토자 하나에게 맡긴다. 쓴 사람은 자기 결과를 좋게 보기 쉽다. 그래서 검토자에게는 결론이 아니라 대상과 근거를 준다.

- 준다: wiki 경로, AGENTS.md 경로, 리포 경로
- 검토자가 할 일
  - 정의마다 `sources`를 열어 실제로 그 말을 하는지 확인한다.
  - 근거 없는 주장, 코드와 다른 정의, 빠진 핵심 정책·흐름을 찾는다.
  - 지적마다 위치와 근거를 단다.
- 검토자는 고치지 않는다. 메인이 지적을 근거로 다시 확인한 뒤 반영하거나 기각하고, 그 이유를 보고에 적는다.
