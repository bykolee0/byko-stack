# Agent Harness Builder

에이전트가 리포에서 일할 때 사람이 같은 설명을 반복하지 않게 하는 것이 목적이다. 그 리포만의 지식(목표·정책·도메인·구조·운영 방법)을 에이전트가 실제로 읽고 따르는 자리에 정리하고, 형식이 무너지지 않게 테스트로 지킨다.

## 왜 이런 모양인가

- **항상 로드되는 자리가 중심이다.** 에이전트는 처음부터 로드된 지시는 잘 따르지만, 열지 말지 스스로 정해야 하는 문서는 잘 열지 않는다. 그래서 중심을 AGENTS.md 하나에 둔다.
  - 거기서 영역마다 "언제 여는지"를 걸어 둔다.
  - 꼭 지켜야 하는 정책은 문서에만 두지 않고 검사로도 막는다.
- **코드를 읽으면 알 수 있는 것은 적지 않는다.** 파일 배치나 보이는 관례가 그렇다. 적을 것은 코드 밖에 있거나 매 세션 다시 파야 하는 것뿐이다. 설명형 개요는 에이전트가 길을 찾는 데 도움이 되지 않았다.
- **wiki는 최종 정의(SSOT)다.** 여기를 보면 결과를 알 수 있어야 한다. 이유와 연결 설명은 정의 아래에 붙는 부차 정보다.
- **결정·작업 기록은 쌓일 뿐 관리할 수 없는 로그다.** 옛 ADR이나 스펙이 그렇다. 관리하는 것은 지금 기준의 정의뿐이다.
- **문서는 낡으면 해가 된다.** 에이전트는 낡은 지시도 그대로 따른다. 그래서 정의마다 근거와 확인 시점을 두고, 형식은 테스트로, 내용은 유지 작업으로 맞춘다.

근거와 이 스킬의 내력은 [references/source-notes.md](references/source-notes.md)에 있다.

## 만드는 것

```
<repo>/
├── AGENTS.md          중심: 개요·목표, 영역 색인, 코드 규칙, 문서 규격, 명령, 미결정, 지식 관리
├── CLAUDE.md          @AGENTS.md (Claude Code는 CLAUDE.md가 있으면 AGENTS.md를 읽지 않는다)
└── docs/
    ├── wiki/          최종 정의(SSOT). 프론트매터 필수, 첫 절은 "## 정의"
    │   ├── policies/  정책(중추) + index.md
    │   └── domain.md · architecture.md · infrastructure.md · deploy.md · testing.md
    ├── records/       결정·작업 기록(로그)
    └── references/    참고 자료(외부 문서, 생성 자료, 이미지) + index.md
검사: 리포 test 도구 안의 하네스 규격 검사 + 꼭 지킬 정책의 강제 검사
```

페이지는 내용이 생길 때만 만든다. 규격과 템플릿은 [references/structure.md](references/structure.md)에 있다. 쓰기 전에 읽는다.

## 어떤 경우인가

| 경우 | 신호 | 읽을 문서 |
|---|---|---|
| 새 개발 리포 | 의미 있는 코드·문서가 아직 없다 | [playbook-new.md](references/playbook-new.md) |
| 기존 개발 리포 | 코드·테스트·CI가 있고 이 하네스는 없다 | [playbook-existing.md](references/playbook-existing.md) |
| 하네스 유지 | AGENTS.md에 이 하네스의 "문서 규격" 절이 있다(wiki 위치는 그 절이 알려 준다). "점검·최신화" 요청도 여기다 | [playbook-maintain.md](references/playbook-maintain.md) |
| 개발이 아닌 리포 | 문서·콘텐츠·데이터가 중심이다(책, 연구, 운영 문서 등) | [non-dev.md](references/non-dev.md) |

여러 경우가 섞여 있으면 가장 가까운 경우를 고르고, 고른 이유를 보고에 적는다. 옛 형태의 하네스(이 스킬의 이전 판이 만든 `docs/design-docs/`, `docs/generated/` 등)가 있는 리포는 "기존 개발 리포"로 다룬다.

기존 리포는 **보완**이 기본이다. 있는 것은 그 자리에 두고 빠진 것만 채운다. 사용자가 **정렬**(기존 문서를 이 구조로 옮기기)을 요청했을 때만 옮긴다.

요청 범위가 좁으면(예: "AGENTS.md만 정리") 그 범위만 하고, 하네스의 나머지는 다음 후보로 보고한다.

## 공통 원칙

1. **근거로 쓴다.**
   - 정의마다 `sources`에 근거를 단다. 코드 경로, 문서, records에 남긴 결정이 근거다.
   - 근거가 없는 정책은 만들지 않는다. 그럴듯한 일반론을 정책처럼 적으면, 다음 에이전트가 그것을 이 리포의 규칙으로 믿는다.
2. **정책 상태는 둘이다.**
   - `confirmed`는 사람이 한 말이나 사람의 결정 기록이 근거인 것이다. 모델이 그 말을 해석해 덧붙인 부분은 `confirmed`가 아니다. 그런 부분은 페이지에 "해석"으로 표시하고 미결정에 확인 항목으로 올린다.
   - `from-code`는 리포 안의 근거(코드·문서·테스트·설정)로 정리한 것이다.
   - 근거가 서로 어긋나면 정책으로 쓰지 않는다. AGENTS.md "미결정"에 무엇이 충돌하는지와 근거 위치를 올린다.
   - 무엇을 정책으로 올릴지는 [playbook-existing.md](references/playbook-existing.md)의 기준을 따른다.
3. **페이지는 내용이 생길 때만 만든다.** 빈 템플릿은 다음 에이전트를 헷갈리게 하고 낡는다.
4. **리포의 기존 관례와 도구가 우선이다.**
   - 같은 역할의 문서가 이미 있으면 이름을 강요하지 않고 색인으로 연결한다.
   - 리포가 쓰지 않는 테스트 프레임워크나 린터는 새로 들이지 않는다.
5. **기존 파일을 지우지 않는다.**
   - 옮기는 것은 정렬 모드에서만, `git mv`로 이력을 남기며 한다.
   - 근거 없이 새로 정해야 하는 결정은 확인 없이 확정하지 않는다. 리포 구조를 바꾸거나 보안·배포·데이터 보존·공개 API에 새 규칙을 두는 것이 그렇다. 확인할 수 없으면 미결정으로 남긴다.
   - 리포가 이미 말하고 있는 것을 정리하는 일은 여기에 들지 않는다.
6. **AGENTS.md는 짧게 둔다.** 200줄 미만(Claude Code 권장), 32KiB 이하(Codex 상한)로 유지한다. 넘치면 세부를 wiki로 옮기고 색인만 남긴다. 이미 있던 AGENTS.md를 줄이는 기준은 [playbook-existing.md](references/playbook-existing.md)를 따른다.
7. **사람이 있는지에 따라 질문 방식을 정한다.**
   - 사람이 없는 실행으로 보는 경우: 요청이 묻지 말라고 하거나, 비대화형 실행(`claude -p`, `codex exec` 등)이거나, 질문할 수단이 없을 때.
     - 질문 때문에 멈추지 않는다.
     - 정할 수 없는 것은 미결정으로 남기고 보고에 적는다.
   - 대화 중인 경우:
     - 조사로 풀 수 없는 것만 묻는다. 기존 리포에서는 근거끼리의 충돌, 새 리포에서는 아직 말하지 않은 결정이다. 한 번에 3개 이내다.
     - 질문과 상관없이 만들 수 있는 것을 먼저 만든다.
     - 답을 받으면 진행하고, 같은 질문을 되풀이하지 않는다.

## 분석과 위임

- **영역별 분석을 나눠 맡긴다.** 기존 리포가 커서 메인이 다 읽기 어렵고 내용이 영역별로 나뉘면, 영역별 읽기 전용 분석을 하위 에이전트에게 나눠 맡긴다. 기준은 영역의 수가 아니라 읽을 양이다. 메인이 다 읽을 수 있으면 직접 읽는 편이 빠르고 싸다. 방법과 위임 지시 형식은 [references/analysis.md](references/analysis.md)에 있다.
- **파일은 메인이 쓴다.** 정의와 형식을 한 손으로 맞추기 위해서다.
- **끝내기 전에 독립 검토를 한 번 받는다.** 새 컨텍스트의 검토자에게 정의와 정책이 `sources`와 실제로 맞는지 대조하게 한다. 리포가 작고 정책이 몇 개뿐이면 직접 대조로 갈음하고, 그렇게 했다고 보고한다.

## 검사

- 하네스 규격 검사를 리포의 test 도구로 만든다. 꼭 지켜야 할 정책은 할 수 있는 만큼 강제 검사로 만든다.
- 사양, 실패 메시지 형식, 언어별 예시는 [references/checks.md](references/checks.md)에 있다.
- Python·Node 예시는 [examples/](examples/)에 있다.

## 완료와 보고

- **완료 조건**
  - 하네스 규격 검사가 리포의 테스트 명령으로 실행되고 통과한다.
  - 기존 테스트와 린트가 통과 상태를 유지한다. 유지 작업에서 새로 생긴 정책 위반으로 실패하는 강제 검사만 예외이고, 보고의 맨 앞에 둔다([checks.md](references/checks.md) "위반이 나왔을 때").
  - 실행할 수 있는 검사가 없으면 "기초만 됨"으로 보고하고, 이유를 미결정에 적는다.
- **보고에 담을 것.** 보고는 요청한 사람의 언어로 쓴다. 리포 문서의 언어와 다를 수 있다.
  - 만들거나 바꾼 파일과 그 목적
  - 생긴 검사와 실행 결과
  - 정책 목록과 상태
  - 미결정과 충돌
  - 확인하지 못한 범위
  - 다음 후보
