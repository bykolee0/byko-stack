# 질문 정책: 조사하고, 제안하고, 필요한 결정만 묻기

goal 설계와 실행에서 사용자의 시간은 사용자가 내려야 하는 결정에만 쓴다.

## 판단 순서

1. 먼저 코드, 문서, 기존 goal, 실제 산출물, 신뢰할 수 있는 출처를 조사한다.
2. 조사 결과 답이 하나로 좁혀지면 채택하고 근거를 기록한다. 질문으로 되돌리지 않는다.
3. 여러 방향이 남으면 2~3개 선택지에 근거, trade-off, 추천을 붙인다.
4. 다음 중 하나라면 사용자 결정을 받는다.
   - 목표, 결과물, 범위 또는 비범위가 달라진다.
   - 품질 기준이나 성공 판정이 달라진다.
   - 새 architecture, dependency 또는 project convention을 도입한다.
   - 공개, 외부 write, 구매, migration, 삭제처럼 되돌리기 어렵다.
   - 비용, 보안, 개인정보, 권한에 실질적인 영향이 있다.
5. 그 밖의 가역적이고 목표 안쪽인 선택은 추천안을 채택하고 `[assumed]`로 기록한다.

`assumed`가 3개 이상 쌓이거나 하나의 가정이 여러 task에 영향을 주면 묶어서 확인받는다. 대화가 불가능한 실행 환경이면 조용히 확정하지 않는다. draft artifact는 남길 수 있지만 state를 `waiting_user`로 두고 journal에 `[decision-required]`를 기록한다.

## 질문 형태

- 조사 없이 열린 질문을 던지지 않는다.
- 한 번에 최대 3개만 묻는다.
- 추천안을 첫 번째로 두고 각 선택지의 영향 차이를 한 줄로 쓴다.
- 답을 기다리는 동안 할 수 있는 read-only 조사나 독립 작업은 계속한다.
- 사용자가 "나중에"라고 하면 `[TBD]`로 남긴다. 목표, 승인 경계, DoD, public API, data model에 영향을 주는 TBD는 실행 전에 해결한다.

## 실행 중 예외

자율 실행을 시작했다는 사실은 새로운 권한을 주지 않는다. 외부 write, destructive action, 결제, credential 사용, scope 확대가 필요하면 상태를 `waiting_user`로 기록하고 정확한 action과 영향을 제시한 뒤 멈춘다.
